## 2. Figure 2 与 AHE 流程

**问**：（附 Figure 2 截图）帮我解释这个图，解释 AHE 的流程。

**答**：

这张图（论文 p.4 的 Figure 2）是 AHE 一轮进化的全景：**用 harness 跑任务 → 把轨迹压缩成证据 → 根据证据改 harness → 下一轮检验这次修改**。图上三种颜色的标签就是三个"可观测性"支柱，分别对应这个闭环里三类需要被看清的东西。

### 2.1 按图从左到右看

**① 左边灰框：NexAU Harness（I. 组件可观测性，蓝色）**
- 框里是被进化的对象：System Prompt、Skills、Tools、Middleware、Sub-agent、Memory。正文说共有 7 类组件，图里把 tool description 和 tool implementation 合成了一个 Tools 图标（p.4，§3.1 第 1 段）。
- 关键在于每类组件都是**固定位置上的独立文件**，组件之间松耦合。比如加一个 middleware 不需要改 system prompt。
- 好处是每种失败模式只对应一类组件，每次修改只落在一个文件上，可以 git diff，也可以按文件回滚（§3.1 第 2 段）。
- 第 1 轮的起点是最小种子 NexAU₀：只有一个 bash 工具，没有 middleware、skills、memory（§3.1 第 3 段）。

**② 中间：Coding Agent ↔ Environment（跑任务）**
- 用当前 harness 装配出 Coding Agent，在沙箱环境里做 Terminal-Bench 2 的 89 个任务，每个任务跑 k=2 次。对应 Algorithm 1 的 phase 1 ROLLOUT。
- 双向箭头表示智能体和环境在多轮交互：执行命令，再看结果。

**③ Raw trace（约 1000 万 tokens）**
- 所有 rollout 的原始轨迹量非常大，有用的信号埋在里面。这正是论文说的三个难点之一。
- 这一步还会先把轨迹规范化，对应 phase 2 CLEAN。

**④ Agent Debugger → Overview（约 1 万 tokens）（II. 经验可观测性，紫色）**
- 用另一个智能体（Agent Debugger）分析轨迹。轨迹被组织成文件系统，每条消息一个文件，Debugger 用 shell 去翻；同一个任务的多条轨迹放在一起，便于对比（§3.2）。
- 产出分两层：
  - 每个任务一份分析报告，写明失败或成功的根因，以及 pass/fail 状态；
  - 一份基准级的 overview，作为每轮的入口文档。
- 从约 1000 万 tokens 压缩到约 1 万 tokens，是一个"可下钻"的结构：先看 overview，需要时再看单个任务的报告，再需要时看原始轨迹。
- 这也解释了图里为什么 **Raw trace 还有一条箭头直通 Evolve Agent**：原始轨迹仍然提供给 Evolve Agent，供它核实报告里的说法（p.5，§3.2 续段）。不过 Evolve Agent 的 prompt 要求先读 analysis，只有分析缺失时才回头看原始轨迹（p.20，B.2）。

**⑤ Evolve Agent（做修改的智能体）**

它有三路输入，图中三条箭头汇到它身上：
1. **Overview / 分析报告**：本轮哪些任务失败、为什么失败；
2. **Raw trace**：需要时下钻核实；
3. **History**（左下角的分支图标）：过去各轮改过什么、哪些有效、哪些被回滚。实现上就是 workspace 的 git 历史和 `evolution_history.md`（p.18，B.2 目录结构）。

它的工作是：把失败归成若干模式类，找出根因，决定在哪一层组件上修，然后修改文件（phase 5 EVOLVE）。

**⑥ 底部：Evidence + Modify Component（III. 决策可观测性，棕色）**
- **Modify Component**：Evolve Agent 的修改通过最外层那条大回路写回左边的 harness。每个逻辑修改对应一次 git commit（phase 6 COMMIT）。
- **Evidence**：每个修改都必须附一条 change manifest，写明失败证据、根因、修复方式、预测能修好哪些任务、可能把哪些任务改坏（§3.3 第 3 段；JSON 格式见 p.21）。
- 这条 manifest 的意义在于下一轮可以检验它：下一轮跑完后，系统把"预测修好 / 预测改坏"的任务和实际变化求交，逐条判定，没起作用的修改按文件回滚（phase 3 ATTRIBUTE + ROLLBACK）。论文的说法是，每个编辑都成了一份"可证伪的契约"，而不是事后给自己找理由。

### 2.2 把图翻成 Algorithm 1 的一轮（p.5）

```
第 t 轮：
1. ROLLOUT     用 H_{t-1} 对每个任务跑 k 次            ← 图中 Coding Agent ↔ Environment
2. CLEAN       规范化轨迹                              ← Raw trace
3. ATTRIBUTE   用本轮结果检验上一轮 manifest 的预测    ← 底部 Evidence 回到下一轮
   ROLLBACK    回滚被判定无效的修改
4. DEBUG       Agent Debugger 分层蒸馏                 ← Agent Debugger → Overview
5. EVOLVE      读证据和历史，修改组件，写新 manifest   ← Evolve Agent → Modify Component
6. COMMIT      git 打标签；若 pass@1 创新高，记为 H_best ← History
```

有一个顺序细节：**归因（第 3 步）在蒸馏（第 4 步）之前**。这样"上一轮哪些修改有效"的结论会进入本轮证据，Evolve Agent 一开始就能看到自己上次的预测准不准。

### 2.3 用论文里的真实案例走一遍（Appendix C.1.2，path-tracing）

1. **跑任务**：第 4 轮，path-tracing 两次 rollout 都失败（0/2）。
2. **轨迹里的问题**：智能体已经渲染出正确的 `/app/reconstructed.ppm`，自检也通过了，最后却执行 `rm -rf … /app/reconstructed.ppm …` 来"收拾干净"，结果 verifier 找不到输出文件。
3. **Debugger 归因**：多个任务都有这个跨任务的失败模式，即"验证通过后又破坏了状态"。
4. **Evolve Agent 修改**：分两层修。
   - chg-7 改 prompt：告诉模型"验证通过后的状态就是交付物，不要动"；
   - chg-8 改 tool：在 shell 工具里装一个守卫，拦截删除受保护输出的命令。
   - 理由是 prompt 里原本就有类似的劝告，但没有执行层面的强制，所以必须在 tool 层兜底。这正好体现了组件可观测性的用处：能判断该修哪一层。
5. **manifest 预测**：能修好 path-tracing、polyglot-rust-c、configure-git-webserver、large-scale-text-editing 等 4 个任务。
6. **下一轮检验**：path-tracing 变成 2/2，polyglot-rust-c 和 large-scale-text-editing 也修好了；configure-git-webserver 只部分恢复，因为守卫可以被 override token 绕过。到第 8 轮，Evolve Agent 把这个绕过口改成了硬拦截。

### 2.4 一句话理解这张图

AHE 的出发点是：**自动进化 harness 卡在"看不清"，而不是"不够聪明"**。所以它让三样东西都对另一个智能体可读：
- harness 是什么：组件文件化；
- 跑得怎么样：轨迹蒸馏成分层证据；
- 改了什么、为什么改、改得对不对：manifest 加下一轮检验。

另外，论文里 Coding Agent、Debugger、Evolve Agent 用的是同一个基座模型 GPT-5.4（p.2，Figure 1 标题），所以分数提升只能归因于 harness 的修改，而不是用了更强的分析模型。

还有一处要注意：图上看不出闭环的短板。论文发现第 ⑥ 步里，"预测修好哪些任务"大约是随机水平的 5 倍准，"预测改坏哪些任务"只有约 2 倍（§4.4.2）。也就是说，这个闭环对改坏的情况基本看不见，这正是进化曲线时升时降的原因。

## 3. 逐行解析 Algorithm 1

**问**：带我一步一步解析 Algorithm 1。

**答**：

### 3.0 先认清输入和符号

```
Require: 种子 harness H0, 基座模型 M, 基准 D, 每任务 rollout 次数 k, 最大轮数 N
```

| 符号 | 含义 | 论文中的实际取值 |
|---|---|---|
| H₀ | 种子 harness NexAU₀：只有 bash 工具，没有 middleware、skills、memory | §3.1、App. A |
| M | 基座模型，**整个循环中固定不变** | GPT-5.4（high） |
| D | 任务集 | Terminal-Bench 2，89 个任务 |
| k | 每个任务跑几次 | 2（Table 4） |
| N | 迭代轮数 | 10 |
| Hₜ | 第 t 轮改完后的 harness | — |
| Tₜ | 第 t 轮跑出来的轨迹 | — |
| Cₜ | 第 t 轮写的 change manifest，即每条修改及其预测 | — |
| Vₜ | 第 t 轮对上一轮 manifest 的判定 | — |
| Rₜ | Debugger 产出的分层证据：overview 加逐任务报告 | — |

**最容易绕晕的一点：第 t 轮跑的是 Hₜ₋₁，也就是上一轮改出来的 harness。** 每一轮先评测上一轮的成果，再在此基础上产出新的修改。Evolve Agent 的 prompt 里专门强调了这个约定："`input/` 里是上一轮产出、本轮刚评测过的东西，`evolve/` 里是本轮要产出、下一轮才评测的东西"（p.18，B.2 "Loop convention"）。

### 3.1 第 1 行：初始化最优记录

```
1: H_best ← H0
```
先把种子当作目前最好的 harness。论文最后报告的 AHE 就是循环返回的 H_best（§4.2 第 1 段："the best resulting configuration is reported as AHE"）。

### 3.2 第 3 行：Phase 1 ROLLOUT，跑任务

```
3: T_t ← ROLLOUT(M, H_{t-1}, D, k)
```
- 用模型 M 加 harness Hₜ₋₁ 组成 Coding Agent，把 89 个任务各跑 k=2 次。
- 每次 rollout 都在一个全新的 E2B 沙箱里执行，由 Harbor 判定 pass/fail，单任务超时 3600 s（App. A）。

**为什么 k ≥ 2？** 论文给了两个理由（p.5，算法后第 1 段）：
1. 每个任务都有一个通过率，而不只是一个 0/1 结果，pass@1 因此更稳；
2. 会出现"部分通过"的任务（1/2），同一个任务成功和失败的轨迹放在一起对比，最容易找到分歧点。Evolve Agent 的 prompt 说这类任务"最有价值"（p.20）。

### 3.3 第 4 行：Phase 2 CLEAN，清洗轨迹

```
4: T_t ← CLEAN(T_t)
```
把轨迹规范成统一格式，去掉没用的内容。原始轨迹也会保留，所以 Debugger 和 Evolve Agent 能同时拿到原始版和"轻度处理版"（§3.2 续段）。

### 3.4 第 5–10 行：Phase 3 ATTRIBUTE + ROLLBACK，检验上一轮的契约

```
5: if t ≥ 2 then
6:   V_t ← ATTRIBUTE(C_{t-1}, T_{t-1}, T_t)
7:   H_{t-1} ← ROLLBACK(H_{t-1}, V_t)
8: else
9:   V_t ← ∅
```
这是 AHE 和"让 LLM 自己反思"类方法最不一样的地方。

**第 6 行在做什么：**
- 三个输入的含义：
  - Cₜ₋₁：上一轮写的 manifest，每条修改都标了 `predicted_fixes` 和 `risk_tasks`；
  - Tₜ₋₁：上一轮的轨迹，即修改**之前**的 harness（Hₜ₋₂）的表现；
  - Tₜ：本轮的轨迹，即修改**之后**的 harness（Hₜ₋₁）的表现。
- 比较 Tₜ₋₁ 和 Tₜ，可以得到每个任务的变化：哪些从失败变成通过，哪些从通过变成失败。
- 拿这些变化去和"预测修好的任务"、"预测有风险的任务"两个集合求交，就得到每条修改的判定 Vₜ（§3.3 第 3 段）。

**第 7 行：** 判定无效的修改，在 Hₜ₋₁ 上**按文件回滚**。因为组件是独立文件、每个修改是一次 commit（§3.1），回滚只需要撤销对应的 commit。

**第 8–9 行：** 第 1 轮没有上一轮的 manifest，只有种子的成绩，所以判定为空。

**为什么归因放在蒸馏之前？** 这样 Vₜ 会作为输入进入第 12 行的 EVOLVE，Evolve Agent 一开始就看到"我上次说能修好的，到底修好没有"。按论文的说法，manifest 由此变成"契约而不是事后的说辞"（p.5，算法后第 1 段）。

Evolve Agent 的 prompt 把这个判定落实为三种处理（p.20，第 9 条）：
- **KEEP**：有效，保留；
- **IMPROVE**：方向对，继续细化；
- **ROLLBACK + PIVOT**：在这一层组件上修不好，回滚后换一层组件重新尝试。

### 3.5 第 11 行：Phase 4 AGENT DEBUGGER，分层蒸馏

```
11: R_t ← AGENTDEBUGGER(T_t)
```
- 把同一任务的多条轨迹放进一个"文件化环境"，每条消息一个文件。Debugger 是一个智能体，用 shell 翻这些文件，找失败根因或成功模式，为每个任务写一份报告（§3.2）。
- 再把所有报告汇总成一份 `overview.md`，作为本轮入口。
- 数据量从约 1000 万 tokens 压到约 1 万 tokens（Figure 2）。
- 运行参数：并发 16，单任务 600 s 超时（App. A）。

### 3.6 第 12 行：Phase 5 EVOLVE，改 harness

```
12: (H_t, C_t) ← EVOLVE(H_{t-1}, R_t, V_t)
```
- **输入**：回滚之后的 Hₜ₋₁、本轮证据 Rₜ、上轮判定 Vₜ。另外它还能读 `evolution_history.md` 和原始轨迹（p.18、p.20）。
- **输出**：
  - 新 harness Hₜ；
  - 新 manifest Cₜ，每条修改都写明失败模式、修改的文件、预测修好的任务、风险任务、改在哪一层、为什么选这一层（JSON 格式见 p.21）。
- **硬约束**（§3.3 第 2 段、p.21）：
  - 只能写 workspace；
  - 不能改模型和 LLM 配置、verifier、tracer；
  - 不能删除种子 prompt 的原有规则；
  - 不能写针对具体任务的逻辑，不能从轨迹反推测试用例。

  这些约束保证分数提升只能来自 harness 本身。

### 3.7 第 13 行：Phase 6 COMMIT

```
13: COMMIT(H_t, C_t, t)
```
在 git 里给这一轮打标签。每个逻辑修改各自是一次 commit（`chg-N: ...`，p.20），这样第 7 行的回滚才能精确到单个修改。

### 3.8 第 14 行：更新最优记录

```
14: if PASS@1(T_t) > PASS@1(H_best) then H_best ← H_t
```
如果本轮跑出的 pass@1 创了新高，就更新 H_best。最后第 17 行返回 H_best。

### 3.9 串起来：前 3 轮的时间线

| 轮次 t | 跑的是 | 归因检验的是 | 产出 |
|---|---|---|---|
| 1 | H₀（种子），得到 69.7% | 无（V₁ = ∅） | H₁ + C₁，例如 prompt 加 8 条规则、shell 工具加可调超时（Fig. 8） |
| 2 | H₁ | C₁：对比 T₁ 和 T₂ | 回滚 C₁ 中无效的修改，产出 H₂ + C₂ |
| 3 | H₂ | C₂：对比 T₂ 和 T₃ | 产出 H₃ + C₃ |
| … | … | … | … |

可以用论文里的数字核对：N = 10 轮中，第 2 到第 10 轮都有归因，共 **9 次**。§4.4.2 和 Appendix D 说自我归因是在"**9 evaluation rounds**"上统计的，两者一致。

另外有一个组件不在算法里：一个一次性的 explore agent 和第 1 轮并行运行，从 NexAU 源码和公开资料中生成几个 skills 给 Evolve Agent 参考。这些 skills 没有特殊保护，从第 2 轮起同样可以被保留、修改或删除（p.5 末段）。

### 3.10 按字面读时值得留意的三处

以下是对伪代码字面含义的观察，论文没有专门讨论这些问题，实际实现可能与字面写法不同。

1. **第 14 行的下标不一致。** PASS@1(Tₜ) 衡量的是 Hₜ₋₁ 的表现，但被记为最优的却是 Hₜ，也就是刚改完、还没评测过的版本。按评测结果严格对应，应该是 H_best ← Hₜ₋₁（而且是回滚之前的那个版本）。
2. **最后一轮的产出 H_N 从未被评测。** 10 轮循环评测的是 H₀ 到 H₉，H₁₀ 写出来后循环就结束了。
3. **回滚之后的 harness 本身也没有被评测过。** 第 7 行回滚后得到的 Hₜ₋₁ 和第 3 行实际跑分的 Hₜ₋₁ 不是同一个版本，下一轮评测的是"回滚加新修改"叠在一起的结果。

第 3 点和论文的一个结论有关：每一轮的分数变化都混合了"撤销旧修改"和"加入新修改"两种效果。再加上 §4.4.1 发现组件之间不是简单相加的，这可能是逐条归因本身就有噪声的原因之一。这一点是推论，原文没有这样说。

**自检问题：** 第 6 行 ATTRIBUTE 为什么需要 Tₜ₋₁ 和 Tₜ 两份轨迹？如果只给 Tₜ，会丢掉什么信息？

## 4. 三个 RQ 分别回答什么、用什么实验

**问**：帮我解析一下论文的三个 RQ 是分别想解决什么问题？作者是用什么实验来回答每个 RQ 的？

**答**：

三个 RQ 构成一条递进的论证链：

- **RQ1：AHE 有没有用？**
- **RQ2：它的效果是真本事，还是只拟合了进化用的那批任务？**
- **RQ3：效果从哪里来，这个闭环本身靠不靠得住？**

后一个 RQ 都在回应前一个 RQ 留下的疑问。

### 4.1 RQ1：为什么用 AHE，而不是人工 harness 或其他自动化方法？

**想解决的问题**：论文要先证明自动进化 harness 这件事值得做。需要回答两个怀疑：
1. 人工精心设计的 harness（如 Codex）已经很强了，自动进化能比它好吗？
2. 已经有自进化方法（ACE、TF-GRPO），AHE 这种"联合进化全部组件"的做法有必要吗？

**实验设计（§4.2，Table 1，Figure 1）**：
- **任务**：Terminal-Bench 2 的 89 个任务，按难度分 Easy 4 / Medium 55 / Hard 30。
- **对照组分两类**：
  - 人工设计的 harness：OpenCode、Terminus-2、Codex；
  - 自进化方法：ACE、TF-GRPO。它们和 AHE 一样**从同一个种子 NexAU₀ 出发**，区别只在进化循环本身。
- **控制变量**：AHE 的三个角色智能体都用 GPT-5.4 high（Figure 1 标题），排除"用了更强的分析模型"这种解释。
- **指标**：pass@1，按难度分别报告。Figure 1 还画了 10 轮中每轮的 pass@1，展示增益是逐步累积出来的。

**结果**：

| 方法 | All | Hard |
|---|---|---|
| NexAU₀（种子） | 69.7% | 51.7% |
| Codex | 71.9% | **56.7%** |
| ACE | 68.9% | 48.9% |
| TF-GRPO | 72.3% | 55.6% |
| **AHE** | **77.0%** | 53.3% |

- AHE 的总分最高。唯一的例外是 Hard 档略低于 Codex，作者用 RQ3a 的消融来解释：单独换入 memory，Hard 档就能达到 63.3%，所以问题出在组件之间相互干扰，并非缺少能力。
- 关于为什么能赢过 ACE 和 TF-GRPO，作者的解释是"改的层不同"：那两个方法只改 prompt 或上下文，不动 tools 和 middleware，而 AHE 的增益恰好集中在那些层。这个解释要到 RQ3a 才有证据支持。

**留下的疑问**：AHE 是在这 89 个任务上进化的，最终报告的也是在这 89 个任务上分数最高的那一版（§4.1、§4.2）。光看 RQ1，分不清这是真实的提升，还是对这批任务的过拟合。这正是 RQ2 要回答的问题。

### 4.2 RQ2：AHE 会不会过拟合它的优化目标？

**想解决的问题**：AHE 的 harness 是在"TB2 任务 + GPT-5.4 high"这一个组合上进化出来的。问题有两层：
- 换一个任务面，它还有效吗？
- 换一个基座模型，它还有效吗？

作者想证明进化出的组件编码的是**通用的工程经验**，而不是针对某个基准的调参（Abstract）。

**实验设计：把 harness 冻结后直接迁移，不再进化（§4.3）**

*实验 A：跨基准迁移（Table 2，Table 5）*
- 把在 TB2 上进化出的 harness 原样拿到 SWE-bench-verified：500 个任务，7 个仓库。
- 对照组是种子 NexAU₀，以及同样在 TB2 上进化出来的 ACE 和 TF-GRPO。四列都用 GPT-5.4，基础设施相同。
- 指标：成功率、每试次 token 数，以及附录里的 Succ/Mtok（每百万 token 的期望成功数）。

*实验 B：跨模型迁移（Figure 3）*
- 把同一套 AHE harness 放到 5 个替代基座上：GPT-5.4 medium / xhigh（同家族），qwen-3.6-plus、gemini-3.1-flash-lite、deepseek-v4-flash（跨家族）。
- 每个基座都同时跑 NexAU₀ 和 AHE，成对比较。

**结果**

跨基准：

| | 成功率 | Tokens（千） |
|---|---|---|
| NexAU₀ | 75.2% | 526 |
| ACE | 74.6% | 679 |
| TF-GRPO | 74.2% | 582 |
| **AHE** | **75.6%** | **461** |

- ACE 和 TF-GRPO 的成功率**跌到种子以下**，token 却多花 11%–29%。作者的解释是：这两个方法从 TB2 学到的东西是文本，每次调用都随 prompt 一起发送，换了任务面就只增加成本，不改变行为。
- AHE 的成功率最高，token 比种子少 12%。

跨模型：5 个基座全部有正增益。跨家族的增益（+5.1 到 +10.1 pp）大于同家族（+2.3 pp）。作者的解释是：离饱和越远的模型，越依赖固化在 tools、middleware、memory 里的协调模式。

**留下的疑问**（个人读法）：
- 跨基准时，AHE 的成功率只比种子高 0.4 pp（75.6% 对 75.2%），论文没有给显著性检验或方差。这一组更有说服力的部分是"**没有变差，而且更省 token**"，以及 ACE、TF-GRPO 确实变差了，而不是 AHE 的成功率明显更高。
- 同家族内增益不单调：high 档 +7.3，medium 和 xhigh 各 +2.3。作者承认这里混入了一个因素：步数预算和超时是按 GPT-5.4 high 拟合的。所以跨模型的数字同时包含"harness 能迁移"和"运行参数是否匹配"两件事（Limitations "Evolution operating point."）。

### 4.3 RQ3：AHE 内部是什么在起作用？它的自我归因可靠吗？

这个 RQ 分成两个子问题，分别检验第 3 节中作者最看重的两个设计：组件解耦，以及自己声明预测、下一轮检验（§4.4 开头）。

#### RQ3a：增益落在哪些组件上？（§4.4.1，Table 3）

**想解决的问题**：AHE 同时改了 4 层。到底哪一层在起作用？RQ1 里"只改 prompt 不够"的说法对不对？

**实验设计**：单组件替换消融。在种子 NexAU₀ 上**只换入一个** AHE 组件（memory、tool、middleware 或 system prompt），其余三个保持种子状态。

**结果**：

| 变体 | All | Hard |
|---|---|---|
| NexAU₀ | 69.7% | 51.7% |
| + memory only | 75.3% | **63.3%** |
| + tool only | 73.0% | 46.7% |
| + middleware only | 71.9% | 50.0% |
| + system_prompt only | **67.4%**（−2.3） | 46.7% |
| AHE full | 77.0% | 53.3% |

两个发现：
1. **增益来自 memory、tools、middleware**，system prompt 单独换入反而退步。作者的解释是 prompt 里 79 行的通用规范，要靠另外三层组件才能落实。这为 RQ1、RQ2 中"层不同"的解释提供了证据。
2. **组件之间不是简单相加的**：三个单组件增益相加是 +11.1 pp，完整 AHE 只有 +7.3 pp。Hard 档上 memory-only 甚至超过了完整版，原因是多个组件都在推动收尾验证，导致重复检查，浪费了步数。这也解释了 RQ1 里 Hard 档的例外。

**个人读法**：这是"只加一个"的消融，而不是"从完整版里去掉一个"的消融。它衡量的是每个组件**单独**的价值，不是在完整系统中的**边际贡献**。既然已经发现组件之间不可加，两种消融的结论可能不同，论文没有做后一种。

#### RQ3b：自我归因有多可靠？（§4.4.2，Figure 4，Appendix D）

**想解决的问题**：AHE 的核心卖点是"每个编辑都是可证伪的契约"。那么 Evolve Agent 写下的预测到底准不准？如果不准，决策可观测性就只是形式。

**实验设计**：
- 拿第 N−1 轮 manifest 中的预测（`predicted_fixes` / `risk_tasks`）对比第 N 轮的实际变化。
- 在 89 个任务上分别计算"修复"和"回归"两类预测的 precision 与 recall，共 9 轮，再与随机预测基线比较。

**结果**：

| | Precision | Recall | 相对随机基线 |
|---|---|---|---|
| 修复预测 | 33.7% | 51.4% | 约 5 倍 |
| 回归预测 | 11.8% | 11.1% | 约 2 倍 |

- 修复是**有依据地瞄准**的，不是猜的。
- 回归基本**看不见**：附录 D 显示，9 轮共做了 43 条回归预测，只命中 5 条；实际发生了 40 个没有预见到的回归。
- 作者把这一点和 Figure 1 中进化曲线的非单调联系起来，并提出"提前预见回归"是未来自进化循环最明确的方向。

**个人读法**：原文没有说明随机基线是怎么构造的，例如是否按每轮预测的数量随机抽取任务。所以"5 倍"和"2 倍"这两个倍数的含义，取决于一个原文未交代的设定。

### 4.4 总览

| RQ | 回应的疑问 | 实验 | 主要证据 | 结论 |
|---|---|---|---|---|
| RQ1 | AHE 比现有方法强吗？ | TB2 上与 3 个人工 harness、2 个自进化方法对比 | Table 1，Fig. 1 | 总分最高（77.0%），Hard 档略低于 Codex |
| RQ2 | 是不是只拟合了 TB2 + GPT-5.4 high？ | 冻结 harness，迁移到 SWE-bench-verified 和 5 个基座 | Table 2/5，Fig. 3 | 没有变差且更省 token；所有基座都有正增益 |
| RQ3a | 增益落在哪一层？ | 单组件替换消融 | Table 3 | 增益在 tools / middleware / memory；组件之间不可加 |
| RQ3b | 可证伪契约可靠吗？ | 预测与实际的 P/R 对比，以随机预测为基线 | Fig. 4，App. D | 预测修复较准，预测回归基本失效 |

论证上的分工是这样的：RQ1 给出"有效"，但留下过拟合的疑问；RQ2 回答这个疑问；RQ3a 为 RQ1 和 RQ2 里"因为改的是更深的层"这一解释补上证据；RQ3b 则拿 AHE 自己的核心机制开刀，直接指出了这个方法的短板。

**自检问题：** 如果想证明 Table 3 中的 system prompt "要靠另外三层才能落实"，单组件替换实验能否单独支撑这个说法？还需要补哪一组消融？

## 5. 实验结果能否完全支持作者主张

**问**：作者的实验结果能完全支持其主张吗？

**答**：

### 5.0 结论先说

**部分支持。**
- **证据较扎实的**：在 TB2 上，AHE 比种子和两个自进化基线强；冻结后迁移不会变差，而且更省 token。
- **证据明显不足的**：论文最核心的主张——"三根可观测性支柱是增益的来源"——**没有被直接检验**。另外有几处措辞比数据走得更远。

下文中标注"原文"的是论文事实，其余是评估者的判断。

### 5.1 主张与证据对照表

| # | 作者主张 | 支持程度 | 主要问题 |
|---|---|---|---|
| 1 | 10 轮把 TB2 pass@1 从 69.7% 提到 77.0%，超过所有基线 | 较强，但有选择偏差 | 只跑了一次进化；在同一批任务上选出 10 轮中最好的一版并报告；没有置信区间 |
| 2 | 超过人工设计的 Codex（71.9%） | 中等 | Codex 等人工 harness 用的基座模型原文未说明 |
| 3 | 冻结后迁移到 SWE-bench-verified，"总成功率最高" | 字面成立，推论偏弱 | 只比种子高 0.4 pp，很可能在噪声范围内；省 token 才是可靠的发现 |
| 4 | 跨三个模型家族 +5.1 到 +10.1 pp，说明编码的是"通用工程经验" | 方向可信，解释偏事后 | 每个基座只跑一次；"离饱和越远增益越大"与数据并不单调吻合 |
| 5 | 增益落在 tools / middleware / memory，不在 system prompt | 在 TB2 上成立 | 只做了"单独加入"的消融；prompt 本来就是围绕其他组件进化出来的 |
| 6 | 结构化的组件能跨任务、跨模型迁移，散文式策略不能 | **弱** | 消融只在 TB2 + GPT-5.4 high 上做过，没有在迁移场景重复 |
| 7 | **瓶颈是可观测性，不是智能体能力**（核心论点） | **未检验** | 没有任何一根支柱的消融 |
| 8 | 进化"不会退化成试错" | 部分成立，作者也承认 | 预测修复的命中率只有约 1/3，回归基本预见不到 |

### 5.2 最关键的四个问题

**问题 1：核心论点没有消融（主张 7）**

论文的核心判断是"瓶颈在可观测性"（p.2，§1 第 4 段），方法的三根支柱就是为此设计的。但实验中**没有**以下任何一组：
- 去掉 Agent Debugger，让 Evolve Agent 直接读原始轨迹（检验经验可观测性）；
- 去掉 manifest 和归因回滚（检验决策可观测性）；
- 把组件耦合在一起，或者只开放 prompt（检验组件可观测性）。

RQ3b 只说明了"预测修复比随机准"，并**没有**说明"有归因回滚的循环比没有的循环进化得更好"。原文也没有报告一共回滚了多少条修改。

所以严格地说，实验证明的是"**AHE 这一整套系统**有效"，而不是"**可观测性**是有效的原因"。

**问题 2：选择偏差和噪声（主张 1）**

原文事实：
- 进化和最终报告用的是**同一批 89 个任务**（p.6，§4.1）；
- 报告的是 10 轮中**最好**的配置（p.6，§4.2 第 1 段）；
- 只有"a single AHE campaign"，没有置信区间和显著性检验。

轮与轮之间的波动不小：Appendix C.1.4 提到第 7 轮从 75.8 跌到 73.0，第 8 轮又到 76.97（p.30–31）。

粗略估算（基于假设）：每个任务跑 k=2 次，假设约 30 个任务的通过概率在 0.5 附近，单轮 pass@1 只由 rollout 随机性带来的标准误就在 2 pp 左右。从 10 次有噪声的评测里取最大值，即使完全没有真实进步，也会系统性地偏高几个点。

7.3 pp 的提升大概率不全是噪声，Figure 1 也显示了上升趋势。但"77.0%"这个具体数字应该被视为**有乐观偏差的上限**。更干净的做法是：用新的 rollout 重新评测最终的 harness，或者把 TB2 拆成进化集和测试集。

**问题 3：迁移结论的措辞强于数据（主张 3、4、6）**

- **SWE-bench**：75.6% 对 75.2%，相差 0.4 pp。7 个仓库里，3 个小仓库上 AHE 低于种子，最大差 6.3 pp（scikit-learn 87.5% 对 93.8%）。"总成功率最高"字面上是对的，但不足以支撑摘要里"编码了通用工程经验"的推论。真正可靠的结论是：**没有变差，并且省了 12% 的 token**，而 ACE 和 TF-GRPO 确实变差了。
- **跨模型的解释**：作者说"离饱和越远的基座越依赖 AHE"（p.7）。看数据：

  | 基座 | 种子分数 | 增益 |
  |---|---|---|
  | gemini-3.1-flash-lite | 36.5% | +5.1 |
  | deepseek-v4-flash | 51.7% | +10.1 |
  | qwen-3.6-plus | 56.2% | +6.3 |

  离饱和最远的 gemini，增益反而小于 deepseek，关系并不单调。同家族内部的不单调，作者又用"运行参数是按 high 档拟合的"来解释。两套解释合在一起，几乎能容纳任何结果，所以是事后解释，不是被检验过的假设。
- **主张 6**（"结构跨任务、跨模型可迁移，散文不行"，p.2 第 5 段）：支撑它的 Table 3 只在 TB2 + GPT-5.4 high 上做过。"跨任务、跨模型"这半句是外推，没有对应实验。

**问题 4：消融的设计限制了它能下的结论（主张 5）**

- 这是"在种子上只加一个组件"的消融，测的是每个组件**单独**的价值。作者自己也发现组件之间不可加（+11.1 对 +7.3），所以单独价值不等于在完整系统里的贡献。缺少"从完整版里去掉一个"的消融。
- system prompt 是和其他三层**一起进化**出来的，作者自己也说它"能否执行取决于另外三个组件"（p.8）。把它单独拿出来测，结果为负，只能说明"这份 prompt 离开配套组件就不行"，**不能**推出"散文式策略本身不能承载增益"。
- −2.3 pp 的退步也很可能在噪声范围内。

### 5.3 其他值得核对的点

- **基线公平性**：ACE 和 TF-GRPO 跑了几轮、用了多少算力，原文未说明。如果 AHE 的预算明显更多，"layer mismatch"（改的层不同）就不是唯一的解释。
- **"层不同"的解释没有被直接测试**：如果把 AHE 限制成只能改 prompt，再和 ACE 对比，就能直接检验这个解释，原文没有做。
- **评测任务的信息可能渗进 memory**（推断）：Evolve Agent 读的就是这 89 个任务的轨迹。memory 里新增的 12 条"边界情形教训"（例如 performance margin、queued-over-limit cancellation，p.8），从描述看相当贴近具体任务，而 memory-only 恰好是 TB2 上增益最大的单组件。prompt 里禁止反推测试用例，但这只是一条 prompt 约束。迁移实验能部分缓解这个担心，但 SWE-bench 上的成功率增益太小，不足以完全打消它。
- **推理档位要回 PDF 核对**：§4.1 说三个角色都用 GPT-5.4 "at the high reasoning setting"，但抽取的 Table 4 文本里出现了两处 "Reasoning effort xhigh"。抽取后的版面已错位，无法确认这两处属于哪个 agent。如果 Evolve Agent 或 Explore Agent 实际用的是 xhigh，Figure 1 标题中"增益只来自 harness 编辑，而非分析器或编辑器能力"的说法就要打折扣。建议直接看 PDF 第 16 页确认。

### 5.4 作者自己已经承认的部分

这篇论文的自我批评比较充分，以下几点不应算作"隐瞒"：
- Hard 档低于 Codex（§4.2）；
- 组件之间不可加（§4.4.1）；
- 回归预测基本失效（§4.4.2，App. D）；
- 运行参数与模型耦合、基准范围有限、护栏不完整（Limitations）。

问题主要出在**摘要和引言的措辞**（"general engineering experience"、"factual harness structure transfers…whereas prose-level strategy does not"）比正文的证据更强。

### 5.5 要让主张站得住，最该补的实验

1. **三根支柱各自的消融**：直接检验核心论点，这是最重要的一项。
2. **多次独立进化，加上 TB2 进化集 / 测试集划分**：给出方差，并消除选择偏差。
3. **用新的 rollout 重新评测最终 harness，并报告置信区间**。
4. **"去掉一个"的消融**，并在 SWE-bench 和其他基座上重复：检验主张 6。
5. **算力对齐的基线**，以及 **AHE-prompt-only 对比 ACE**：检验"层不同"的解释。
