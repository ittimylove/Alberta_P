## 〇、核心想法：先定责，再修复

### 核心概念

**定责（blame assignment）**：修 harness 之前，先确定这次失败"该由谁负责"。

### 一句话版本

> 我们可以用模型 M、harness H 运行任务，得到失败轨迹 τ。
>
> 现有工作（ECDYSIS、SE、HarnessCompass）的做法是**根据 τ 直接修改 H**。
>
> 但在修改之前，我们可以先在**失败的那一步**做两次"换位"实验：
>
> 1. **换掉模型的动作**：harness 不变，把模型在这一步的动作换成标准动作，经过 H 重新执行。
>    → 如果成功，说明 H 能支持正确的做法，**错在模型**。
> 2. **换掉 harness 的转述**：模型的动作不变，把 H 的执行结果和反馈，与环境中**实际发生的情况**直接对比。
>    → 如果不一致，说明 H 执行或反馈有误，**错在 harness**。
>
> 问题是：**如果只让"错在 harness"的失败去修改所有模型共用的那部分 harness，演化出的 harness 换给没参与演化的模型时，会不会比 ECDYSIS 更好，而且更便宜？**

### 两次换位组成的 2×2 定责表

| | **换掉模型动作后成功** | **换掉模型动作后仍失败** |
|---|---|---|
| **harness 转述与环境一致** | **错在模型** → 放进模型专属层，或改写成引导形式 | **错在任务或环境本身** → 剔除，不修改 |
| **harness 转述与环境不一致** | **错在 harness** → 修复后放进共用核心 | **错在 harness**（任务本身也可能有问题）→ 先修 harness，再复查 |

### 与第六节四项检验的对应关系

| 换位实验 | 对应检验 |
|---|---|
| 换掉 harness 的转述 | T1 执行忠实性 + T2 观测忠实性 |
| 换掉模型的动作 | T3 参考动作回放 |
| 修改生成后的安全检查 | T4 修改可接受性（修改不能缩小政策允许的动作集合） |

### 三个案例走一遍【假设】

| 案例 | 换掉 harness 的转述 | 换掉模型的动作 | 定责 |
|---|---|---|---|
| **A：退款**（p.14） | 一致：退款确实按模型的选择执行了 | 换成"退回原支付方式" → 成功 | **错在模型**。修改未通过 T4（删掉了合法选项），改写为"用户没指定时先询问" |
| **B：空操作写入**（p.14–15） | **不一致**：模型请求的是"不变"，环境里却多了一条支付记录 | — | **错在 harness** → 加拦截规则，放进核心 |
| **C：取消订单**（p.14） | **不一致**：提示说"可以取消"，工具实际拒绝 | — | **错在 harness** → 修正提示，放进核心 |

### 为什么这个想法尖锐

1. **可以证伪**：如果定责之后，演化出的 harness 在没参与演化的模型上并没有变好，想法就不成立。
2. **直接回应现有工作的缺口**：ECDYSIS 自己说需要"显式失败归因"（p.2 第 5 段），但其 FDCR 提示词里并没有任何归因分类（仓库 `src/ecdysis/fdcr/roles.py`，已核实）。定责就是把这个"显式归因"真正做出来。
3. **有现成的实现基础**：τ²-Bench 提供标准动作序列，其评估器本身就是"在新环境中执行标准动作再比较数据库"（已核实，见第十三节），两次换位实验都能在此基础上实现。
4. **概念好记**：一句话即可讲清——先定责，再修复。

## 一、问题陈述

> 在失败驱动的 harness 演化中，能否**直接检验 harness 与环境契约是否一致**（而不是通过模型行为间接推测），在修改 harness 之前，把每个失败自动归入"harness 缺陷 / 模型局限 / 任务或环境问题"，并据此决定每条修改的**生效范围**和**形式**，从而提升演化出的 harness 在未参与演化的模型上的效果？

### 最终目的

让演化出的 harness 在**未参与演化的模型**上也表现好（跨模型泛化）。归因只是手段，归因结果用来决定每条修改**放在哪一层、以什么形式生效**，而不是简单地删掉 MSA。

### 核心洞见（v1 → v2 的关键转变）

ECDYSIS 对 HLR 的定义是：

> 环境规则或执行证据表明，harness 在解析、状态维护、接口语义、执行条件或反馈呈现上有错误或遗漏（p.14）。

这是 **harness 与环境契约**（政策规则、工具真实语义、状态变化）之间的性质，**与模型无关**。

- v1 用"不同模型的行为"去**间接推测**这个性质，因此出现盲区：harness 有缺陷但只有弱模型触发（案例 B）、harness 没问题但所有模型都失败（共有弱点）。
- v2 **直接检验这个性质**；跨模型复发不再用于归因，而是用于它真正擅长的问题：**一个模型局限是所有模型共有，还是演化模型独有**。

### 表述上的注意点

- MSA 不等于有害。ECDYSIS 承认 MSA 也可能有效且可跨任务复用（p.14）；其数据也显示 w/o FDCR 的 MSA 比例（75.61%）高于 SE（60.00%），但跨模型平均准确率（64.56%）也高于 SE（58.67%）（p.7 Table 1；p.20 Table 10）。因此 MSA 比例只作**诊断指标**，不作优化目标。

## 二、场景

**典型使用方式**：用一个便宜的模型把 harness 演化好，冻结后部署到多个模型上。

| 论文 | 演化用的模型 | 迁移到的模型 |
|---|---|---|
| ECDYSIS | 仅 Qwen3-8B（p.16，Appendix C） | Qwen3-14B、Qwen3-32B、MiniMax-M2.7、Llama-3.1-8B |
| HarnessCompass | 仅 GPT-5.4 | Claude-Sonnet-4.6 |
| Life-Harness | 仅 Qwen3-4B-Instruct（演化 LLM 为 GPT-5.5，原文 p.6） | 另外 17 个开源模型（原文 p.6，已核实） |

**矛盾**：演化时看到的每个失败都只来自一个模型，但演化出的 harness 要服务多个模型。

## 四、现有工作及其遗漏

### 4.1 各工作的归因与处理方式

| | ECDYSIS | HarnessCompass | SSA | HarnessEvolve |
|---|---|---|---|---|
| 是否自动演化 | 是 | 是 | 否（人工设计） | 是 |
| 运行时是否区分 harness 缺陷 / 模型局限 | **否**；人工审计标签只用于事后统计 MSA 比例（p.14） | 是，但靠**失败模型自我归因**（harness / 自身推理 / 任务歧义 / 环境） | 否；提出 intent-execution gap 概念，但**没有诊断方法** | **否**；只归纳错误类型（如工具幻觉、参数遗漏、过早终止）【待核实】 |
| 用什么证据 | 跨任务复发（同一模型） | 模型自报 + 轨迹核实 | 作者经验 | 失败轨迹与参考轨迹的**第一个分歧点**（由 LLM 比较）【待核实】 |
| 对模型局限类修改的处理 | 降低权重，有复发证据就保留（p.3） | 非 harness 原因的反馈可丢弃 | 放进家族适配器 | 不区分 |
| 修改的生效范围 | 一律全局 | 一律全局 | 核心 / 家族适配器 | 一律全局（每个模型单独优化）【待核实】 |
| 是否测量跨模型伤害 | 否 | 否 | 否 | 否 |

### 4.2 核心遗漏

1. **归因靠间接证据或人工**：ECDYSIS 靠人工事后判断；HarnessCompass 靠失败模型自报（未用人工标签验证准确率）；跨任务复发会被同一模型的弱点放大——只做聚合时 MSA 比例从 60.00% 升到 75.61%（p.20 Table 10）。
2. **没有人直接检验 harness 与环境契约的一致性**：SSA 提出了 intent-execution gap 但没有诊断方法；ECDYSIS 的 HLR 定义正是这个一致性，却只靠人工判断。
3. **处理只有"全局修改或不修改"两种选择**（SSA 例外，但其划分是人工的、家族级的、只涉及提示和接口）。
4. **没有把"任务或环境本身有问题"的失败剔除**：这类失败会被当成修改依据。

## 五、后果

1. **迁移后成绩可能比初始 harness 还差**。ECDYSIS Table 6（p.18），SE 在 τ²-Airline 上：

   | 模型（均未参与演化） | 初始 harness（Human-Aug.） | SE 演化后 |
   |---|---|---|
   | Qwen3-14B | 38.33% | **23.33%** |
   | MiniMax-M2.7 | 81.67% | **73.33%** |

   原文未把退步归因到具体修改，但这与"MSA 导致 harness 与演化模型耦合"的预期一致【推断】。
2. **合法动作空间被缩小**：案例 A 把一个模型的局部错误固化成对所有模型生效的全局禁令（p.14）。
3. **过程无法监控**：MSA 比例只能事后人工统计，训练中无法及时停止或回滚。
4. **补救成本高**：FDCR 把 MSA 比例压到 45.45%，代价是 τ²-Retail 上 API 成本从 $2.485 增到 $5.763（p.20 Table 9），且 FDCR 仍无任何来自环境契约或其他模型的直接证据。

## 六、方法框架

### 6.1 把 harness 看作两个映射

| 映射 | 方向 | 需要满足的性质 |
|---|---|---|
| **执行映射** | 模型的意图 → 环境中实际发生的变化 | 实际变化与模型的意图一致，没有隐藏的副作用 |
| **观测映射** | 环境的真实状态 → 返回给模型的信息 | 返回的信息真实、完整，与环境实际行为一致 |

对应 SSA 的 intent-execution gap 的两个方向。由此：

- **HLR**：至少一个映射不忠实；
- **MSA**：两个映射都忠实，但模型自己选错了。

### 6.2 四项可自动执行的检验

| 检验 | 时机 | 做法 | 抓住的情况 |
|---|---|---|---|
| **T1 执行忠实性** | 修改前 | 对模型实际执行的动作，比较环境状态变化（state diff）与动作声明的语义：是否有意料之外的变化？这些变化是否反馈给了模型？ | 案例 B |
| **T2 观测忠实性** | 修改前 | 将 harness 给模型的陈述（提示中的规则、工具反馈文本）与环境实际行为对比，必要时直接调用工具验证 | 案例 C |
| **T3 参考动作回放** | 修改前 | 若 T1、T2 都通过，在失败步骤上把模型的动作换成参考动作，在当前 harness 下执行，看能否成功 | 参考动作成功 → MSA；参考动作也失败 → 任务或环境问题 |
| **T4 修改可接受性** | 修改后 | 检查修改是否缩小了政策允许的动作集合 | 案例 A |

T3 的"失败步骤"可直接采用 HarnessEvolve 的做法定位：失败轨迹与参考轨迹的**第一个动作分歧点**（见第十节）。

### 6.3 四分类路由

| 归因结果 | 判定条件 | 处理方式 |
|---|---|---|
| **HLR** | T1 或 T2 不通过 | 修复后放进**通用核心** |
| **通用的 MSA** | T1–T3 判为 MSA，且**多个模型都失败** | 放进**通用核心**，只用**引导**形式，不用限制形式 |
| **专属的 MSA** | T1–T3 判为 MSA，且**只有演化模型失败** | 放进**模型专属适配层** |
| **任务或环境问题** | T3 中参考动作也失败 | **剔除**，不修改 harness |
| （任意类别） | 修改未通过 T4 | 拒绝，或改写成不缩小动作空间的形式 |

**跨模型复发的新角色**：只在"通用的 MSA"与"专属的 MSA"之间做区分，不再参与 HLR 的判定。因此参照模型只需在被判为 MSA 的失败上运行，成本低于 v1。

**分层架构**：借鉴 SSA 的"共享核心 + 适配器"结构（事件循环、反馈语义作核心；提示、接口作适配器）。分层本身**不是本问题的贡献**，本问题的贡献是**为分层提供自动的、有证据支撑的路由机制**。

## 七、为什么 v2 比 v1 强

| 盲区 | v1：仅用跨模型复发 | v2：基于契约的归因 |
|---|---|---|
| 只有弱模型会触发的缺陷（案例 B） | 漏判 | **T1 能抓到**，不依赖其他模型是否失败 |
| 所有模型共有的弱点 | 误判为 HLR | **T3 判为 MSA**，跨模型信号再归为"通用的 MSA" |
| 任务歧义或标准答案有误 | 误判为 HLR | **T3 参考动作也失败 → 剔除** |
| 同家族模型失败相关 | 信号被夸大 | 归因不依赖模型；只在判断 MSA 作用范围时受影响 |
| 看不到修改的性质（案例 A） | 看不到 | **T4 专门检查** |
| 成本 | 参照模型要跑完整训练任务 | T1、T2、T4 只需读状态和调用工具；T3 只回放单步；跨模型运行只对 MSA 部分需要 |
| 与 ECDYSIS 人工定义的关系 | 间接近似 | **直接把定义操作化**：HLR 的"环境规则或执行证据证明 harness 有错"即 T1、T2 检验的内容 |

**故事线**：ECDYSIS 用人工判断"缺陷是否得到确认"，SSA 提出 intent-execution gap 但没有诊断方法，HarnessEvolve 用参考轨迹定位分歧点但不做归因；本工作**把三者统一起来，做成可以自动执行的检验**，再用跨模型信号决定迁就的作用范围。

## 八、形式化

- **输入**：初始 harness H；演化模型 m₀；参照模型集合 M = {m₁, …, m_k}（便宜、来自不同家族）；训练任务集 D；环境 E（可读取状态）；每个任务的参考轨迹；环境政策 P。
- **对每个失败 f**：
  1. 用 T1、T2 检验执行映射与观测映射的忠实性；
  2. 若都忠实，定位第一个分歧点，用 T3 回放参考动作；
  3. 若判为 MSA，查询参照模型是否复现该失败。
- **输出**：每个失败的四分类标签及置信度；每条修改的生效层（核心 / 适配层）与形式（限制 / 引导）。
- **目标**：在演化预算受限的条件下，最大化演化出的 harness 在**未参与演化的模型**上的留出成绩。
- **诊断指标（不作优化目标）**：MSA 比例、合法动作空间缩小程度、推理 token 开销、被剔除的任务比例。

| 编号 | 子问题 | 可检验的假设 |
|---|---|---|
| RQ1 | T1–T3 的归因与人工标签一致性如何？ | 一致性高于跨任务复发（ECDYSIS）、模型自我归因（HarnessCompass）、跨模型复发（v1） |

| RQ4 | T4 把限制型修改改写成引导型后，对未参与演化的模型有何影响？ | 改写后，未参与演化的模型成绩不低于不改写的情况，且演化模型上的收益基本保留 |
| RQ5 | 四分类路由（核心 / 适配层）与"一律全局保留"（ECDYSIS 式）、"直接丢弃"（HarnessCompass 式）、人工划分（SSA 式）相比，效果如何？ | 在未参与演化的模型上优于前两者，且不劣于人工划分 |
| RQ6 | 参照模型的数量和家族对"通用 / 专属 MSA"划分的影响？ | 一个不同家族的小模型即可拿到大部分收益 |

## 十、与 HarnessEvolve 的重叠分析

HarnessEvolve（arXiv:2609.00829，2026-09-01）【以下关于参考轨迹的生成与用法已对照 PDF 原文核实，见第十三节；实验设置部分仍来自抓取工具摘要】：

- **参考轨迹的来源**：让**同一个执行 agent 在拿到标准答案的情况下**运行任务得到（§3.2），并由评估 agent 检查它不是走捷径得到的（§3.3）；在优化循环开始前**预先生成并缓存**。
- **参考轨迹的用法**：由优化 agent（LLM）比较失败轨迹与参考轨迹，找出**第一个动作分歧点**并视为根因，之后的分歧视为连锁效应（§3.4）；错误被聚类成系统性失败模式。
- **其他机制**：质量闸门（检查数据泄漏、提示膨胀）与性能闸门（当前批次提升且近期批次不退化）（§3.5）。
- **实验**：SearchQA、OfficeQA、SpreadsheetBench 及两个内部数据集；模型 Qwen3.6-27B、DeepSeek-V4-Flash；报告了**跨框架**迁移，**未报告跨模型迁移**（每个模型单独优化）。

### 重叠程度

| T3 的组成部分 | HarnessEvolve 是否已有 | 说明 |
|---|---|---|
| 使用参考轨迹 | **有** | 必须引用并说明区别 |
| 定位失败轨迹与参考轨迹的第一个分歧点 | **有**（由 LLM 比较） | T3 可直接借用这一步来确定"在哪一步回放" |
| 在当前 harness 下**重新执行**参考动作（反事实回放） | **没有** | 参考轨迹只是预先缓存、用于比较，从未在 harness 下回放 |
| 据回放结果区分 harness 缺陷 / 模型局限 | **没有** | 只归纳错误类型，不区分 harness 与模型 |
| 区分并剔除"任务或环境问题" | **没有** | 拿不到验证过的参考轨迹时（5 次尝试后），只是退回单轨迹分析 |
| 检查状态副作用、提示与工具一致性、动作空间缩小（T1、T2、T4） | **没有** | — |

**结论：中等重叠，集中在"原料"层面，不在"目的"层面。** HarnessEvolve 已经有参考轨迹和分歧点定位，但用它们做的是**错误诊断**（这一步错在哪），而不是**归因**（错误该由 harness 还是模型负责）。T3 的新意在于**反事实回放**和**基于回放结果的归因**，必须在论文中明确这一区别，并承认借用了分歧点定位。

### 一个可以利用的细节【推断】

HarnessEvolve 的参考轨迹是"**同一个模型拿到标准答案后**"跑出来的。这本身就隐含了一个粗粒度的 T3：

- 拿到答案后能成功 → 说明当前 harness **能够**支持正确路径；
- 拿到答案后 5 次都失败 → HarnessEvolve 只把它当成"没有参考轨迹"的退化情况处理，但这恰恰可能意味着 **harness 缺陷，或任务 / 环境本身有问题**。

HarnessEvolve 没有利用这个信号。v2 可以把它纳入 T3，作为轨迹级别的补充检验。

## 十一、依然存在的弱点与前提

| 弱点 / 前提 | 说明 |
|---|---|
| **依赖可读取的环境状态** | T1 需要 state diff。**已核实**：τ²-Bench 的 `Environment` 提供 `get_db_hash()`、`set_state()`（可按消息历史回放到任意时刻）、`make_tool_call()`，评估器 `evaluator_env.py` 本身就是"在新环境中回放标准动作、比较数据库哈希"，T1 与 T3 在技术上可行。SWE-bench 等代码环境的"状态"更难定义 |
| **依赖参考动作** | T3 需要参考动作。**已核实**：τ²-Bench 的 `tasks.json` 在 `evaluation_criteria.actions` 中提供标准动作序列，Airline 50 个任务中 43 个有、Retail 114 个中 112 个有；没有的多为"应拒绝用户请求"类任务，需另行处理（可借鉴 HarnessEvolve 的"给答案后生成参考轨迹"） |
| **标准动作不与轨迹逐步对齐** | τ²-Bench 的标准动作是整条任务的动作序列，不标注对应原轨迹的哪一步；T3 需先用分歧点定位（HarnessEvolve 做法）把标准动作与失败轨迹对齐 |
| **回放需经过 harness** | τ²-Bench 评估器自带的标准动作回放是在**裸环境**上执行的；T3 要检验的是 harness，回放必须经过 harness 的动作层（如 Life-Harness 的 Action Realization Layer），需要自己写适配 |
| **只能做单步局部回放** | 回放一步后，后续状态会与原轨迹分叉，只能检验分歧点这一步 |
| **"声明的语义"需要定义** | T1 判断"意料之外的变化"需要知道每个工具声明的效果。案例 B 较简单（参数等于当前值即"不变"），一般情况可能需要用 LLM 从工具文档中抽取，这一步本身可能出错 |
| **政策需要可被机器检验** | T4 需要"政策允许的动作集合"。τ²-Bench 的政策是自然语言文本，需先抽取成规则 |
| **新颖性** | 已确认与 HarnessEvolve 中等重叠（见第十节）；SSA 的 intent-execution gap 是概念来源，需引用 |

## 十二、验证方案

### 12.1 对比的归因方法

| 方法 | 来源 |
|---|---|
| 跨任务复发 | ECDYSIS |
| 模型自我归因 | HarnessCompass |
| 参考轨迹分歧点诊断 | HarnessEvolve |
| 跨模型复发 | v1 |
| **基于契约的归因（T1–T4）+ 跨模型决定作用范围** | 本问题 v2 |

### 12.2 指标

- **归因准确率**：按 ECDYSIS 的审计协议（p.14）标注 ground truth；重点报告**危险象限**的召回率。
- **最终效果**：演化出的 harness 在**未参与演化的模型**上的留出成绩（AVG / Pass@3 / Pass^3）。
- **成本**：演化阶段 API 成本、参照模型运行次数、端到端训练时间。
- **诊断指标**：MSA 比例、动作空间缩小程度、推理 token 开销、被剔除任务比例。

### 12.3 最小可行实验

- **设置**：τ²-Airline 和 τ²-Retail；Qwen3-8B 为演化模型；初始 harness 采用 ECDYSIS 的 Human-Aug.。
- **步骤**：
  1. 用 Qwen3-8B 跑一遍训练任务，收集失败；
  2. 对每个失败执行 T1、T2、T3；
  3. 按 p.14 的审计协议人工标注同一批失败（或其引发的修改决策）；
  4. 比较 T1–T3 的归因与人工标签的一致性，重点看案例 B 类失败是否被 T1 抓到。
- **继续做下去的条件**：T1–T3 与人工标签的一致性明显高于跨任务复发；危险象限的召回率可接受。
