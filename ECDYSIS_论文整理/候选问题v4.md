# 候选问题 v4：先定责，再修复（一页版）

> 基于 [候选问题_v2.md](候选问题_v2.md) 第〇节浓缩。"p.X" 指 ECDYSIS（arXiv:2609.11677v2）页码；【假设】= 尚未实验验证。

## 问题陈述

我们用模型 M 在 harness H 上得到失败轨迹 {τ}，现有工作根据 {τ} 修改 H，再把 H 交给其他模型 M′ 使用。

**能否在修改 H 之前，先用环境中的实际情况判定每个失败"该由 H 负责还是由 M 负责"，只用"H 的错"去修改共用的 H，使没跑过演化的 M′ 直接受益？或者说，M′ 上不需要再跑演化，就能拿到修改带来的好处，而不被 M 的错拖累？**

## 核心假设【假设，待第 6 节验证】

| 编号 | 假设 | 如果不成立 |
|---|---|---|
| **H1** | {τ} 中有相当一部分是 **M 自己的错**；把它们用来修改共用的 H，会让 M′ 变差。迹象：SE 演化出的 harness 在没参与演化的模型上退步（p.18 Table 6） | 这个问题不值得做：直接根据 {τ} 修改 H 就够了 |
| **H2** | "该由谁负责"可以通过环境中的实际情况**直接检验**：在 H 下回放标准动作，并把 H 的执行结果和反馈与环境对照（需覆盖失败之前的全部步骤，见第 5 节），不需要依赖模型自我报告或人工审计 | 方法不成立：定责结果与人工标签的一致性不高于 ECDYSIS 的跨任务复发 |
| **H3** | 只用"H 的错"修改共用的 H，演化出的 H 在 M′ 上的成绩**高于** ECDYSIS，且演化成本**不高于** ECDYSIS w/ FDCR | 方法有效但没用：定责准确，却换不来更好的跨模型效果 |

---

## 1. 场景

一个 agent 产品上线后，同一个 harness 往往要同时对接多个底座模型：简单请求走便宜的小模型、复杂请求走大模型；不同客户指定不同厂商的模型；主模型出故障时切到备用模型。

演化 harness 时，为了控制成本，通常只用其中一个模型去跑失败、改 harness，改完的 harness 却要给所有模型用。现在只有两种做法：

- **每个模型各演化一遍**：成本随模型数量线性增长。Better Harnesses, Smaller Models（arXiv:2607.08938）就明确说，每换一个模型都要重新优化一遍；
- **用一个模型演化完，直接给所有模型用**：省钱，但其他模型可能被拖累。ECDYSIS 中，用 Qwen3-8B 演化出的 SE harness，在 τ²-Airline 上让 Qwen3-14B 从 38.33% 降到 23.33%，MiniMax-M2.7 从 81.67% 降到 73.33%（p.18 Table 6）。

也就是说，组织要么为每个模型付一次演化成本，要么接受"为一个模型修好、其他模型变差"的风险。

## 2. 缺口

| 现有工作 | 怎么判断失败该由谁负责 | 缺什么 |
|---|---|---|
| ECDYSIS | 运行时**不判断**；MSA/HLR 只在事后由人工审计（p.14） | 作者自己说需要"显式失败归因"（p.2 第 5 段），但 FDCR 提示词中没有任何归因分类（仓库 `fdcr/roles.py`，已核实） |
| HarnessCompass | 由失败的模型**自己报告**原因 | 自我归因的准确率未经人工标签验证 |
| HarnessEvolve | 用参考轨迹定位**第一个分歧点** | 只诊断"错在哪一步"，不判断"该由谁负责"；从不在 harness 下回放参考动作（原文 p.5、p.13，已核实） |

**共同缺口**：没有人在修改之前，用环境中的实际情况**直接检验**失败该由谁负责。

## 3. 后果

- **迁移后反而变差**：SE 演化出的 harness 在没参与演化的模型上退步。τ²-Airline 上，Qwen3-14B 从 38.33% 降到 23.33%，MiniMax-M2.7 从 81.67% 降到 73.33%（p.18 Table 6）。
- **一个模型的错被固化成全局规则**：退款案例删掉了政策允许的礼品卡选项，所有模型都受影响（p.14）。
- **复发信号放大模型弱点**：只做跨任务聚合时，MSA 比例从 60.00% 升到 75.61%（p.20 Table 10）。
- **补救昂贵**：FDCR 把 MSA 压到 45.45%，但 τ²-Retail 的演化成本从 $2.485 增到 $5.763（p.20 Table 9）。

## 4. 方法：两次换位 → 2×2 定责

| | 把模型动作换成标准动作后**成功** | 换成标准动作后**仍失败** |
|---|---|---|
| harness 的执行与反馈**与环境一致** | **错在模型** → 放进模型专属层，或改写成引导形式 | **错在任务或环境** → 剔除 |
| harness 的执行与反馈**与环境不一致** | **错在 harness** → 修复，放进共用核心 | **错在 harness** → 先修，再复查 |

修改生成后再加一道检查：**不得缩小政策允许的动作集合**（防止退款案例那样的全局禁令）。

## 5. 最强反例：先误导，后出错

**情形**：harness 在**更早的步骤**（如系统提示）给了模型错误信息，模型据此在后面某一步做出合理但错误的动作。

**以案例 C 为例**（p.14）：系统提示说"修改过的订单仍可取消"，取消工具实际会拒绝。模型照着提示去取消，在这一步与标准动作分歧。

- 若只在**分歧那一步**检验：工具如实返回了"拒绝"，执行与反馈都和环境一致；把动作换成标准动作后成功。
- → 2×2 判定为 **"错在模型"**，被放进模型专属层。
- **实际上是 harness 的错**，而且其他模型同样会被这条错误提示误导，却得不到修复。

**为什么这是最强反例**：它攻击的是一句话版本中"**在失败的那一步**做换位"这一设计，而且发生在论文自己的案例上；后果是把真正的 harness 缺陷错放进专属层，正好违背"让其他模型受益"的目的。

**修补方向**：
1. "harness 是否与环境一致"的检验不能只看分歧那一步，要覆盖**分歧之前的全部前缀**，包括系统提示和每一步反馈中关于工具和政策的陈述；
2. 若前缀中存在与环境不一致的陈述，且模型的分歧动作恰好依赖这条陈述，则判为 **"错在 harness"**。

**次强反例**：harness 的反馈**完全真实但难以使用**（例如返回很长的原始数据，关键字段被淹没），所有模型都出错。检验会判为"错在模型"，但 ECDYSIS 的 HLR 定义包含"反馈呈现"问题（p.14）。v2 的处理是：跨模型一致失败 → 归为"通用的模型局限" → 以引导形式放进核心。结果仍可接受，但**定责标签与人工标注不一致**，评估时要单独统计这一类。

## 6. 最小验证

| 项目 | 内容 |
|---|---|
| **环境与模型** | τ²-Airline（训练 30 题）、τ²-Retail（训练 74 题）；Qwen3-8B；初始 harness 采用 Life-Harness 公开的演化后 harness |
| **故障注入（有标准答案）** | 向 harness 植入 4 类已知缺陷：① 反馈与工具行为矛盾；② 静默的状态副作用；③ 截断的输出；④ **系统提示中的错误陈述**（专门检验最强反例） |
| **自然失败（人工标注）** | 抽取 40–50 个自然失败，2 人按 ECDYSIS p.14 协议独立标注，报告 Cohen's κ |
| **对比方法** | 跨任务复发（ECDYSIS）；模型自我归因（HarnessCompass 式）；只检验分歧那一步的定责；**检验全部前缀的定责** |
| **指标** | 注入缺陷中被判为"错在 harness"的比例（召回率）；与人工标签的一致率 |
| **继续做下去的条件** | ① 全前缀定责对注入缺陷的召回率明显高于其他方法，且能抓到第 ④ 类；② 与人工标签的一致率高于跨任务复发 |
| **不成立的信号** | 第 ④ 类缺陷仍大量被判为"错在模型"，或定责结果与人工标签的一致性不高于跨任务复发 |

通过后再做第二步：用定责结果引导演化，比较演化出的 harness 在**没参与演化的模型**上的成绩与演化成本（对比 ECDYSIS w/ FDCR）。
