| 场景与输入 | 在固定任务集上进行多轮、跨会话的离线演化，演化期间 task model 固定不变；输入是完整的执行轨迹、verifier 分数和跨轮的历史记录 |

## 一、场景与输入

### 1.1 在什么情况下适配？

| 子问题 | 回答 | 原文依据 |
|---|---|---|
| 动机场景 | 模型版本、工具或问题领域发生变化时，现有 harness 需要定制修改 | p.3，§1 第 2 段 |
| 适配方式 | 多轮、基于轨迹的学习过程，跨会话持续演化；论文以此区别于只在单个会话内运行的 Dynamic Workflows | p.4，§2.1 第 5–6 段 |
| 适配所用的数据 | 一个固定的任务集（adaptation batch），每轮都完整重新评估，不做抽样 | p.15，§6.1 *Benchmarks* 段；p.28，附录 A.2 |
| 轮次与停止条件 | 最多 T = 15 轮；连续 P = 3 轮没有采纳修改就提前停止 | p.15，§6.1 *Benchmarks* 段；p.9，算法 1 第 29 行 |
| 本轮是否修改 | 需要依次满足三个条件：Digester 判断可行动性 a_t ≥ α，Planner 给出非空的 landscape，Evolver 至少产生 1 个候选；之后还必须通过 Critic 和确定性门控 | p.9，算法 1 第 7–28 行；p.11，§4.4 |
| 阈值 α 的取值 | **未说明** | — |
| 模型在适配期间是否变化 | harness 演化期间模型固定（“the model M is fixed throughout evolution”）；协同演化时放开这一限制 | p.8，§4.1 *MDP instantiation* 段；p.12，§5.1 第 1 段 |
| 任务集异质时 | 可选用变体隔离：最多维护 K 个 harness 变体，按任务簇路由 | p.11，§4.5 第 1–2 段 |
| 是否在部署时（测试时）适配 | 不在部署时适配：部署时演化好的 harness 是静态制品，不需要 meta-agent 推理 | p.22，§7.5 第 4 段 |

## 二、修改对象

| 子问题 | 回答 | 原文依据 |
|---|---|---|
| 修改范围 | 整个 harness 配置 H = (c₁, …, c₉)，覆盖九个维度：模型选择、上下文组装、记忆、工具、执行环境、评估与奖励、控制与安全、可观测性、训练桥 | p.7，定义 1；p.6，§3.3 第 1 段 |
| 实际修改了哪些维度 | “AEGIS edits span all nine dimensions”；最常修改的是 D2（上下文组装）和 D4（工具） | p.6，§3.3 第 2 段 |
| 修改的形式 | 代码级制品，由 meta-agent 生成，不从预先列好的选项中挑选：新的 processor 源码、修改后的提示模板、重新配置的工具注册表、控制流重写 | p.8，定义 2 |
| 修改的分类 | 四类（bucket）：prompt、tools、config、processor；一次修改可以跨多类 | p.36，表 9；p.32，附录 B.1 *Manifest shape* |
| 修改的操作 | 在某个 hook 上插入 processor；按 singleton group 替换 processor；删除 processor | p.6，§3.2 第 3 段 |
| 修改的约束 | 必须保持 hook 的类型契约；每个 hook 只允许修改特定字段；singleton group 内互斥 | p.5，表 1；p.6，§3.2 第 2–3 段；p.8，定义 2 |
| prompt | 会修改 | p.36，表 9 |
| skill | 引言把 skills 列为 harness 原语之一，但修改分类中没有 skill 这一类；是否会单独修改 skill，**未说明** | p.3，§1 第 3 段；p.36，表 9 |
| 控制逻辑 | 会修改（控制流重写；新增或替换控制 processor） | p.8，定义 2；p.10，§4.3 *Planner* 段 |
| 记忆策略 | 列为可考虑的结构性修改（memory-policy redesigns）；实验中是否实际修改过记忆，**未说明** | p.10，§4.3 *Planner* 段 |
| 评估与奖励维度（D6） | 定义上属于可修改的维度之一；协同演化中 verifier 必须固定。实验中是否修改过 D6，**未说明** | p.7，定义 1；p.12，§5.1 步骤 2 |
| 各基准实际的修改分布（示例） | GAIA · Sonnet：11 次 prompt、7 次 processor、7 次 config、6 次 tools；τ³-Bench 与 SWE-bench：tools 修改为 0 | p.38，附录 D.1；p.41，附录 D.4；p.42，附录 D.5 |
| 变体 | 变体隔离时，一个修改如果改善部分任务、又让另一部分退化，会分叉出新变体 | p.11，§4.5 第 2 段 |
| 模型权重 | harness 演化时不修改；协同演化时用 cross-harness GRPO 更新模型参数（实验中只用于 Qwen3.5-9B） | p.8，§4.1；p.12–14，§5.1–5.4；p.18，§6.5 |

## 四、成功标准

| 子问题 | 回答 | 原文依据 |
|---|---|---|
| 主指标 | 在各基准 verifier 下的 pass@2 成功率 | p.15，§6.1 *Metrics* 段；p.29，附录 A.3 |
| 报告方式 | Evolved 取演化过程中的**峰值**；Δ = 峰值 − 初始值 | p.16，表 4 标题 |
| 是否修好了原来的失败 | 每个修改在 manifest 中预测会解锁或稳定哪些任务，并给出上线后应在轨迹中出现的特征（attribution signature）；用命中率（实际翻转数 / 预测翻转数）衡量 | p.35–36，附录 B.3，表 9；p.37，附录 D 引言段 |
| 示例 | C-R10-02 预测的 7 个任务中有 5 个翻转为通过，命中率 0.71 | p.37，附录 C.1 *Delta realized* 段 |
| 对其他任务是否有效 | 只在演化所用的同一任务集上衡量；**未见任务没有评估** | p.15，§6.1 *Scope* 段；p.23，§7.7 第 1 条 |
| 防止回归的机制 | seesaw 约束：不得让任何之前已解决的任务退化；manifest 必须列出可能退化的任务（tasks_at_risk）；regressions.md 逐轮列出退化的任务 | p.8，§4.1；p.10，§4.3；p.30，附录 B.1；p.36，表 9 |
| 稳定性指标 | Final − Peak；负值表示灾难性遗忘 | p.17，表 5 标题 |
| 实验中是否出现回归 | 出现了：GAIA · GPT-5.4（Global）从 73.8% 降到 49.5%；τ³ Telecom · Sonnet 在 R7 下降 −14.0，R9 恢复；SWE-bench · GPT-5.4 从 63.6% 降到 50.9% | p.17，表 5、§6.2 *Domain-level variation*、*Post-peak degradation* 段；p.19，§6.6 |
| 回归为何没被拦住 | pass@2 只记录逐任务的二值翻转，低于阈值的耦合会累积而不被发现 | p.19，§6.6 *Catastrophic forgetting* 段；p.23，§7.6 末段 |
| 变体隔离下 | 终值等于峰值（87.4%），没有退化 | p.17，表 5 |
| 噪声与统计 | 单轮通过数变化在 ±5% 以内视为噪声；每单元 3 个随机种子；n = 103 时二项分布 95% 置信区间 ±8.5%、标准误约 3.3% | p.29，表 8；p.17，§6.3；p.18，§6.4 |
| 是否排查 reward hacking | Critic 负责；案例：GAIA R10 上线的修改中，部分任务是靠利用 verifier 的格式规律通过的，R11 被发现，R12 修复 | p.10，§4.3；p.19，§6.6 *Reward hacking* 段 |

## 五、迁移范围

| 换的是什么 | 回答 | 原文依据 |
|---|---|---|
| **task agent 模型** | 同一个 meta-agent（Opus 4.6）为三个家族的 task agent 分别演化 harness，不需要针对家族做适配；但每个模型都是单独演化的。把为一个模型演化好的 harness 直接给另一个模型使用，**未说明** | p.17，§6.2 *Cross-model generalization* 段；p.22，§7.4 |
| **meta-agent 模型** | 所有实验都用 Opus 4.6；较弱的 meta-agent 没有评估；开源模型作为 meta-agent 未测试 | p.22，§7.4 第 2 段；p.23，§7.7 第 3 条 |
| **模型升级（旧 harness 用于新模型）** | 作为动机提到；没有相应的实验，**未说明** | p.3，§1 第 2 段 |
| **任务（同一基准内）** | 未见任务上的泛化未经检验（“plausible but untested”）；部署时，演化集以外的任务路由到总体成功率最高的变体，但没有报告相应结果 | p.23，§7.7 第 1 条；p.22，§7.5 第 4 段 |
| **任务（跨基准）** | 五个基准各自单独演化；把一个基准上演化的 harness 用于另一个基准，**未说明** | p.15，表 3；p.16，表 4 |
| **执行环境** | 执行环境是可修改的维度之一（D5）；每个任务使用全新的环境实例；只测试了离散、文本动作空间，连续动作空间（如机器人控制）未测试；harness 跨执行环境迁移，**未说明** | p.6，§3.3；p.29，附录 A.5；p.23，§7.7 第 2 条 |
| **harness 实现** | 所有实验都在 HarnessX 内部进行；论文从设计上主张“通过组合而非复制来复用”，但没有相应实验。迁移到其他 harness 框架，**未说明** | p.3，§1 第 2 段；p.5，§3 引言段 |
| **协同演化的适用范围** | 只在 Qwen3.5-9B 的 GAIA 和 WebShop 上做过；要求同一方能同时控制 harness 演化和模型训练 | p.18，§6.5；p.23，§7.7 第 4 条 |
| **基准覆盖** | SWE-bench 只用 55 题，τ³-Bench 只有 3 个领域；逆缩放等结论可能无法推广到任务异质程度不同的领域或更大的评估集 | p.23，§7.7 第 5 条 |
