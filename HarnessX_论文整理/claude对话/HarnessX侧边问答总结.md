## 速查：概念一句话

| 概念 | 一句话解释 |
|---|---|
| hook | agent 运行流程上预留的 8 个固定时间点（插槽），每到一个点就发出一个事件 |
| processor | 写在模型外面的一小段代码，挂在某个 hook 上，在那个时刻自动执行，检查或修改模型看到的内容和做出的动作 |
| harness vs. processor | harness 是模型外面的整层框架；processor 只是其中一类部件 |
| change manifest | 每个候选修改附带的、格式固定、事后可以对账的说明（“证据账本”） |
| 冒烟测试 | 上线前确认新代码至少能跑起来、不报错 |
| rollout | 用当前策略实际把任务跑一遍，记录全过程和结果 |
| Digester | “消化器”：把海量原始轨迹压缩成结构化的诊断摘要，并判断本轮是否值得继续 |
| 普通 GRPO | 同一个模型对同一道题采样多次，组内互相比较 |
| cross-harness GRPO | 同一道题在不同 harness（和模型）版本下的轨迹放在一组比较 |
| replay buffer | 存放最近几轮轨迹的共享数据仓库，FIFO，harness 演化和模型训练都从这里取数据 |
| pass@2 | 每题跑两次，有一次成功就算通过 |
| operational mirror | 把 harness 演化类比为符号空间里的强化学习，用来预测会出现哪些问题 |

## 一、hook 与 processor

### 1. “把 processor 挂到 hook 上”是什么意思？
- **hook**：运行循环按固定顺序经过 8 个时间点，每个时间点只允许修改特定内容（p.5 表 1）。

  | hook | 触发时机 | 允许修改 |
  |---|---|---|
  | task_start | 任务开始 | 系统提示词 |
  | step_start | 每一步开始 | 对历史记录做结构性编辑 |
  | before_model | 调用模型之前 | 最后一条用户消息；可追加一条用户消息 |
  | after_model | 模型返回之后 | 回复内容、工具调用 |
  | before_tool | 执行工具之前 | 工具输入、是否批准执行 |
  | after_tool | 工具返回之后 | 工具结果 |
  | step_end / task_end | 每一步 / 任务结束 | 只读 |

- **processor**：接收一个事件，输出零个或多个事件；对事件只能做五种处理之一：透传、变换、拆分、拦截、中断（p.6 §3.2）。
- **“挂上去”**：把 processor 登记到某个 hook，流程每走到那个点就自动执行它。
- **设计理由**（p.6 §3.2）：
  - 同一 hook 上的 processor 输入输出类型相同，所以增、删、换都不会破坏流程的类型正确性。
  - `_singleton_group`（同组互斥）、`_order`（执行顺序）、`_after`（依赖关系）约束 processor 之间如何组合。
  - 违反 hook 契约会立即报错。
- **与演化的关系**：AEGIS 可以在某个 hook 上插入、替换、删除 processor，不用碰其他代码。
- **比方**：hook 是流水线上固定的工位，processor 是装在工位上的检测或加工设备。

### 2. processor 到底起什么作用？
- **核心区别：提示词是“告诉模型应该怎么做”，processor 是“在模型外面用代码保证它这么做”。**
  - 例：要防止 agent 原地打转。写进提示词（ALFWorld 初始提示词第 7 条原则，p.35）只是建议，模型不一定遵守；写成 processor 则由代码强制执行。
- **论文的印证**（p.39 附录 D.2）：
  - 强模型 Sonnet 几乎只靠改提示词就能提升（“consistently obeys them”）。
  - 弱模型 Qwen3.5 需要 processor 做 “a mechanical fix for a failure that prompt-level steering cannot resolve”。
  - 模型越弱，演化越早从提示词引导转向 processor 强制执行。
- **论文中真实出现过的 processor**：

  | 基准 | 作用 | 出处 |
  |---|---|---|
  | ALFWorld（Qwen3.5） | 截取推理文本，补发模型漏掉的工具调用 | p.39 |
  | ALFWorld（GPT-5.4） | 为变换类任务管理步数预算 | p.39 |
  | WebShop | 发现重复搜索或来回翻页时追加警告（advisory processor） | p.40 |
  | τ³-Bench | 在对话中强制执行业务政策的先后顺序 | p.41 |
  | GAIA | BudgetDeadlineProc：上线又撤回两次，R10 被删除（**帮倒忙的例子**） | p.16 图 4；p.36–37 |

### 3. processor 和 harness 的区别
- **结构**（p.5–6 §3.1）：
  ```
  harness H = (M, C)
    ├─ M：模型配置
    └─ C = (P, S)
          ├─ P：挂在 8 个 hook 上的 processor 列表   ← processor 在这里
          └─ S：共享资源（工具注册表、tracer、工作区、沙箱、插件）
  ```
- AEGIS 的修改分四类：prompt、tools、config、processor（p.36 表 9），**processor 只是其中一类**。GAIA 上最成功的修改 C-R10-02 改了 tools、prompt、config 三类，完全没动 processor（p.36–37）。
- **比方**：模型是发动机；harness 是发动机以外的整辆车；processor 是其中的电子辅助系统（自动刹车、车道保持）；提示词是贴在仪表盘上的驾驶须知；工具是车上配的设备。

### 4. processor 就是控制逻辑吗？
- **不完全是。** 原文：“Every per-step behavior in HarnessX is implemented as a processor”（p.6 §3.2）；Figure 1 说九个维度 “each a pluggable processor bundle”。
- processor 是一种**通用的插件格式**，可以实现上下文组装（D2）、记忆（D3）、控制与安全（D7）、日志记录（D8）、训练数据导出（D9）等。
- 之所以前面的例子看起来都像控制逻辑，是因为附录 D 中 AEGIS 为修补失败而加的 processor 恰好以控制和纠偏为主。
- 注意：论文没有逐一列出每个维度对应哪些 processor，按维度举的例子是根据 §3.3 归纳的。

## 二、AEGIS 的流程细节

### 5. change manifest 与冒烟测试
- **change manifest**：论文称为 “the loop's evidence ledger”（p.36 表 9）。

  | 字段 | 通俗理解 |
  |---|---|
  | candidate_id | 编号，如 C-R10-02 |
  | bucket | 改的是哪一类：prompt / tools / config / processor |
  | capability_evidence | “我实际试过，确实能用”的证据 |
  | file_changes | 改动清单 |
  | predicted_impact | 预测哪些任务会解锁、变稳定、有风险（“军令状”） |
  | attribution_signature | 生效后下一轮轨迹里应该出现的特征 |

  - 关键是后两项让每次修改**可以被证伪**。例：C-R10-02 预测的 7 个任务中有 5 个翻转为通过，hit rate 0.71，WikiTextFetch 也确实被调用了（p.37）。
  - 使用者：Critic（对照证据）、门控（第一项检查就是清单是否完整）、后续轮次（按 hit rate 判断哪类修改有效，连续上线但低于 0.4 的就禁止再上线同类修改，p.33）、审计（p.22 §7.6）。
- **冒烟测试**：只检查“能不能跑”，不检查“效果好不好”。
  - 要求：引入新 processor 代码时，必须证明它能实例化，并在合成输入上运行不抛异常（p.10）。
  - 原因：类型系统只保证格式合法，保证不了代码能运行；跑不通的候选会 “burn a round's ship slot for zero flips”（p.32）。
  - Evolver 提示词里分两级（p.32）：
    - **Level 1**：单元调用能工作。
    - **Level 2**：结果能真正传到模型的下一轮输入。例：WikiTextFetch 的返回内容序列化后仍是完整的 10,529 字符（p.37）。
  - 不允许用 try/except 掩盖错误；必须贴出实际运行的命令和输出。
  - 只改提示词的候选不需要冒烟测试。

### 6. rollout 是什么意思？
- 强化学习的基本循环分两步：**rollout**（用当前策略实际跑一遍，收集轨迹）→ **更新**。
- 在 AEGIS 中对应算法 1 第 4–6 行：用 H_t 跑题，拿到轨迹和分数。区别在于，这里被更新的是 harness，模型固定不变（p.8）。
- **重要性**：rollout 是 agent 强化学习里最贵的部分（p.14 §5.4）。协同演化的卖点就是复用 harness 演化时已经跑出的轨迹，“at no additional rollout cost”。

### 7. Digester 是什么？
- 字面意思是“消化器”，是 AEGIS 的第一个阶段，相当于“病历整理员”。
- 为什么需要：GAIA 一轮约产生 10M token 的原始轨迹，直接交给后续阶段会超出上下文，截断又会丢信息；Digester 把它压缩到约 10K（p.10；p.18）。
- 产出：
  - **逐任务摘要**：是否通过、失败类别、涉及的组件、证据摘录。
  - **跨轮历史**：用来区分持续存在的老问题和偶然的噪声。
  - 对应文件：`digests/<task_id>.md`、`overview.md`。
- **可跳过**：同时输出可行动性分数 a_t；低于阈值 α 时本轮直接结束（算法 1 第 8 行）。a_t 的定义和 α 的取值论文都**未说明**。
- 例：附录 C.1 中，Digester 发现所有维基百科抓取都返回 0 字符，这直接促成了 WikiTextFetch（p.36）。

## 三、协同演化与 GRPO

### 8. 普通 GRPO 与 cross-harness GRPO
- **普通 GRPO**（DeepSeekMath，论文引用 [33]）：同一个模型对同一道题独立回答 G 次 → 分别打分 → 组内计算 Â = (r − μ)/(σ + ε) → 提高好回答的概率。不需要价值网络。组内差异**只来自随机性**（p.13：“within-group variation reduces to stochastic sampling”）。
- **cross-harness GRPO**：同一道题在不同 harness（和模型）版本下的轨迹放在一组，组内差异来自**不同做法的好坏**。

  | | 普通 GRPO | cross-harness GRPO |
  |---|---|---|
  | 组内差异来源 | 随机性 | 不同策略的好坏（加上随机性） |
  | 模型学到什么 | 哪次发挥更好 | 哪种做法更好 |

- **比方**：一个学生把同一道题做 8 遍 vs. 带着不同教辅做同一道题，看哪种做法得分高。论文把 harness 称为 “structured exploration operator”（p.14）。

### 9. replay buffer 是什么？
- 一个存放最近几轮轨迹的数据仓库，“replay”指存下来的数据可以反复使用。
- 每轮流程（p.12 §5.1）：运行 → 打分 → 连同 harness 版本一起写入 → AEGIS 读取 → GRPO 读取。**同一份数据，两边共用。**
- 特性：
  1. **容量固定，FIFO**。实验中是最近 4 轮的滑动窗口：GAIA 824 条（103×2×4），WebShop 400 条（p.18）。
  2. **累积多轮**，所以同一道题会有来自不同版本的多条轨迹，这是跨 harness 分组的前提。
- 只保留最近几轮的理由：太旧的数据和当前模型差距过大；最旧的数据最多落后 C/s 轮（p.14）。
- **比方**：一个只保留最近四次考试试卷的文件夹，老师和学生都翻它，不需要额外再考一场。

### 10. buffer 是针对“一个模型 + 一个固定 harness”保存的吗？
- **不是。** 一次实验只有一个 buffer，里面混着多个模型版本和多个 harness 版本的轨迹（p.12 步骤 3；p.13 §5.2；p.14 §5.4）。
- 例（第 6 轮，4 轮窗口）：buffer 里是 (M₃,H₃)、(M₄,H₄)、(M₅,H₅)、(M₆,H₆) 各自产生的轨迹；如果某轮修改被拒绝，相邻两轮的 harness 版本可以相同。
- 混在一起是**有意的设计**：只存一个固定 harness，就退化回普通 GRPO 了。每条轨迹都带版本标记，训练时可以还原到原来的上下文。
- 补充：
  - 不同基准各有各的 buffer（从 824 和 400 的规模推断，原文没有明说）。
  - 只演化 harness 的对照组也用 buffer：模型只有一个版本，harness 有多个版本。

### 11. 为什么 harness 会有不同版本？
- 因为 AEGIS 每轮都在改 harness：H₀ 跑完 → 上线修改 → 变成 H₁ → 用 H₁ 跑 → …
- 如果某轮修改被拒绝，版本不变，所以 buffer 里的版本数可能比轮数少。
- 版本不同不是副作用，而是演化的直接结果，正好为模型提供了可供比较的行为多样性（p.14）。

### 12. “按组采样 → 计算 GRPO 损失 → 更新模型”是怎么实现的？
- **第 0 步：缓存 π_old**。轨迹写入时，用产生它的模型做一次前向计算，把 token 的 log-prob 缓存到磁盘；以前轮次的轨迹复用缓存（p.12 步骤 5；p.14）。原因是 buffer 里混着多个模型版本，事后无法再还原。
- **第 1 步：按任务分组**：G_x = {task(τ) = x}（式 2）。
- **第 2 步：计算组内优势**：Â = (r − μ)/(σ + ε)（式 3）。奖励：GAIA 为 0.9×正确性 + 0.1×格式，WebShop 用原生奖励。
- **第 3 步：在原 harness 上下文下重算当前概率**：每条轨迹用产生它的 H_k 构造提示词、工具 schema 和观测，梯度只作用于模型输出的 token（p.13 *Task-level alignment* 段）。
- **第 4 步：计算损失并更新**：ρ = π_θ/π_old；J = E[min(ρÂ, clip(ρ,1−ε,1+ε)Â)] − β·D_KL(π_θ‖π_ref)，π_ref = M₀（式 4–5）。
- **实验设置**：Qwen3.5-9B；优化器批次为整个 buffer；学习率 1e-6；clip 0.2；**KL 系数为 0**；每轮 5 步；8×H100；batch size 256。
- **时序**：AEGIS 和 GRPO 在同一轮内互不依赖，两者都完成后才进入下一轮。
- **未说明的细节**：
  - “按组采样”具体怎么采。
  - 批次大小的矛盾：整个 buffer vs. 256。
  - 损失如何聚合。
  - 工具返回等非模型生成的 token 是否做了掩码。
  - 用的训练框架。
  - 5 步是否在同一批数据上重复更新。

## 四、实验与指标

### 13. “每个单元的随机种子数 = 3”是什么？
- 出自表 8（p.29）。字面理解：每个实验配置（基准 × task agent × 条件）用 3 个随机种子各跑一次。
- 但论文中**看不到它的使用痕迹**：表 4–6 都只报告单个数值，没有均值 ± 标准差。仅有的统计误差（±8.5%、标准误约 3.3%）是根据二项分布算出来的理论值。
- 不要和下面两种重复混淆：pass@2 是每题跑 2 次；协同演化中 GAIA 每轮评估两次取平均。
- 表 8 的版式在文字提取时错位，“种子数 = 3”这个对应关系是按语义还原的，引用前需要对照原 PDF 核实。

### 14. pass@2 的利与弊
- **算法**：每题跑两次，至少一次成功就算通过（p.15；p.29）。
- **好处 1**：减少偶然失手造成的成绩跳动。
- **好处 2**：给每道题一个 0/1 标签，方便 seesaw 约束逐题对比修改前后是否退化。
- **代价**：看不出成功率的细微下降。示例（数字为举例，不是论文数据）：单次成功率从 90% 降到 60%，pass@2 只从 99% 降到 84%，大多数时候仍然记为“通过”。
- **论文中的实例**：
  - τ³ Telecom：连续 5 条提醒规则单独看都没造成退化，第 6 条一加上去就下降 14 个百分点（p.19）。
  - GAIA · GPT-5.4（Global）：退化 “individually undetectable under pass@2's binary signal yet compound into aggregate decline”（p.17）。

### 15. 实验 2（Global vs. Ensemble）讲的是什么？
- **背景**：GAIA 题型杂，修好一类题的修改会弄坏另一类题，这是 GAIA · GPT-5.4 Δ = 0 的原因（p.15）。
- **Global**：全部题目共用一套 harness。修改伤得明显就被拒绝；伤得不明显就被放行，伤害悄悄累积。
- **Ensemble（变体隔离）**（p.11 §4.5）：维护最多 K 套变体，按任务簇路由；“帮一部分、伤另一部分”的修改会分叉出新变体；seesaw 检查按变体分别进行。
- **比方**：全年级只用一本教辅 vs. 按班级分开配教辅。
- **结果**（p.17 表 5）：

  | 策略 | 终值 | 峰值 | 终值 − 峰值 | token |
  |---|---|---|---|---|
  | Ensemble | 87.4% | 87.4% | 0.0 | 107.8M |
  | Global | 49.5% | 73.8% | −24.3 | 143.7M |

  - Global 的峰值 73.8% 就是起点，之后一路下滑，跌幅超过 ±8.5% 的置信区间，属于真正的灾难性遗忘。
  - Ensemble 不退化，峰值出现在 R14，还更省 token：只在所属簇上评估，被拒绝的候选也更少。
- **论文用它说明**：单一 harness 在异质任务上会停滞；类型化组合是变体隔离的前提（p.21 §7.1）。
- **注意**：
  - 只在一个组合上做过。
  - K 的取值和簇的划分方式未找到说明。
  - 【推断】路由和评估用的是同一批题，可能高估成绩；部署到新题上的效果，这个实验无法说明。

### 16. 图 5 的横坐标是什么？
- “Evolution Round”，R0 到 R8，每一格是一轮完整循环。R0 是起点，两条曲线重合（GAIA 约 20%，WebShop 约 36%）。
- 同一横坐标上：AEGIS 曲线是模型冻结、harness 演化了 n 轮；Co-Evolution 曲线是 harness 演化 n 轮，模型也训练了 n 轮（每轮 5 步）。
- 两条曲线在 R0–R3 重合，R4 开始分开（p.19：“coincide until joint training takes effect (R4)”）。【推测】可能需要先积累几轮 buffer 数据，原文没有证实。
- 峰值：GAIA 37.4%（R4）对 41.7%（R4）；WebShop 49%（R6）对 54%（R5）。阴影部分是协同演化多出来的提升。

### 17. “验证 operational mirror 的预测”是什么意思？
- 先用“harness 演化 ≈ 符号空间里的强化学习”这个类比，事先预言会出现三种病理，再去实验日志里找证据。
- 三种病理及对应的防御：reward hacking → Critic；灾难性遗忘 → 确定性门控；探索不足 → Planner（p.9）。
- 找到的案例：GAIA R10–R12（reward hacking）、τ³ Telecom R7（遗忘）、ALFWorld R4–R7（探索不足）。论文结论：“All three pathologies … appear in practice”（p.20）。
- **局限**（p.21–22 §7.3）：
  - 这只是设计启发，不是形式化理论，预测不了哪种病理先出现、何时出现、有多严重。
  - 三种病理有代表性但不完整。
  - 验证方式是挑案例，证明的是“会发生”，不是“发生得有多普遍”。

### 18. “跨会话的离线演化”是什么意思？
- **跨会话**（有原文依据）：轨迹和结论会保存下来，带到下一轮继续改进。论文以此区别于只在单个会话内起作用的 Dynamic Workflows（p.4 §2.1 第 5 段）。
- **离线**（我的归纳用词，原文没有 “offline evolution” 这个说法）：先在固定任务集上集中演化，部署时 harness 是静态文件，不再修改，也不需要 meta-agent（p.22 §7.5）。
- 和 §5.4 的 “offline training compute” 不是一回事，那里指模型训练只复用已有轨迹。
