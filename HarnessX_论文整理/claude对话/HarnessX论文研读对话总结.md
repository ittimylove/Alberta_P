### 2. 摘要讲解：是否修改了模型权重？
- **主体实验没有修改权重。** harness 演化期间模型固定（p.8），+14.5% 完全来自修改提示词、工具、processor 和配置。
- **只有协同演化实验修改了权重**：用 cross-harness GRPO，只在 Qwen3.5-9B 的 GAIA 和 WebShop 上做过，比只演化 harness 再提升 +4.7%。

- 核心是跨 harness 分组：同一任务在不同 harness 版本下的轨迹放在同一组计算相对优势，让模型学到“哪种做法更好”。

### 10. 实验是怎么实现的？
- 框架：meta-agent 固定为 Opus 4.6，3 个 task agent，5 个基准，pass@2，每个任务使用全新的环境实例，两个基线（Static、CC SDK）。

- 不足：
  - 三组消融实验都只在单一设置上做。
  - 协同演化缺少“只训练模型”的对照组。
  - 没有报告多次重复运行的方差。
  - 部分实现细节没有说明。

### 11. 讨论：用旧模型（如 GPT-4）当 meta-agent 会不会更好？
- harness 适配的是 task agent，因为 meta-agent 读的是 task agent 的轨迹，看的是 task agent 的成绩，与 meta-agent 是谁无关。
- 论文没有测试过较弱的 meta-agent（p.22 §7.4）。我的推断是效果大概率会变差：弱模型难以诊断强模型的失败、难以写出能跑通的代码、也难以识别 reward hacking。
- 成本未必更低：候选被拒绝得多，需要的轮数就多，每一轮新模型都要把所有题跑一遍。
- 可能的折中方案：按阶段混用模型；或者只在 task agent 很强、主要靠改提示词的场景下使用便宜的 meta-agent。

## 贯穿全程的关键判断

1. **主结论的边界**：+14.5% 是在固定模型、演化所用的同一任务集上取得的 pass@2 **峰值**，没有留出测试集。
2. **真正被验证的机制**：
   - 变体隔离能防止跨簇遗忘（表 5）。
   - 三种病理在实验中真实出现过（§6.6）。
3. **作者的推测，没有单独验证**：
   - 逆缩放的原因。
   - Digester 是节省 token 的来源。
   - 准确率主要来自基础设施，而不是四阶段架构。
4. **最值得追问的地方**：
   - 候选在上线前还是上线后评估（算法 1 没有写清楚）。
   - 逐个修改的门控拦不住低于阈值的累积退化。
   - 协同演化只验证了“同时突破两个天花板”中的一半。

## 附录：长段落叙事总结（全文）

这篇论文的出发点是：智能体（agent）的能力不只取决于底层模型，还取决于包在模型外面的运行时框架（harness），也就是提示词、工具、记忆和控制流，它们决定了模型如何观察、推理和行动。任务越长、环境越复杂，harness 的设计就越成为智能体开发的核心。现有做法分为两条线：一条是 LangChain、LangGraph、AutoGen 这类基础组件库和编排框架，以及 Claude Code、Cursor 这类产品化 harness；另一条是 APE、OPRO、DSPy 等提示词优化，Memento 等记忆复用，ADAS、AFlow 等工作流搜索，以及 SICA、Darwin Gödel Machine、Meta-Harness 等直接演化 harness 的工作。作者认为这些做法存在三个缺陷：harness 由人手工编写且保持静态，换模型或换任务都要重新定制；提示模板、工具封装、重试策略和记忆写在同一段代码里，彼此纠缠，改一处会悄悄破坏另一处；harness 工程与模型训练互相脱节，轨迹被丢弃，没有用于训练。作者还认为，提示词和工作流优化没有覆盖工具实现和记忆策略，而现有的 harness 演化工作缺少把失败模式和防御手段联系起来的统一理论。需要说明，上述缺陷是作者对已有系统的分析，论文没有用实验逐一证明；真正被实验证实的问题是，在任务异质的集合上，单一 harness 的演化会停滞甚至退化。作者的核心洞察是：harness 演化在结构上可以对应到符号空间里的强化学习，harness 配置是状态，带类型的修改是动作，执行轨迹（trace）加上 verifier 分数是反馈。这样一来，强化学习中的奖励投机（reward hacking）、灾难性遗忘（catastrophic forgetting）和探索不足（under-exploration）就变成了可以提前防御的设计风险；而且在符号空间里这些风险会被放大，因为作为演化者的 LLM 可以构造出结构化的漏洞利用，对共享组件的修改也会产生非局部影响。由此作者提出 HarnessX。它的第一层是组合层：harness 定义为 H=(M,C)，M 是模型配置，C=(P,S)，其中 P 把 8 个生命周期钩子（hook，从 task_start 到 task_end）分别映射到一串处理器（processor），每个钩子只允许修改规定的字段；S 是工具注册表、tracer、沙箱等共享资源。每个处理器接收一个事件，产出零个或多个同类型事件，结果只有透传、变换、拆分、拦截、中断五种。因为输入输出类型相同，插入、替换或删除处理器都不会破坏整条流水线的类型正确性；_singleton_group、_order 等元数据防止冲突的重复组件，行为空间则被划分为模型选择、上下文组装、记忆、工具、执行环境、评估、控制与安全、可观测性、训练桥九个维度。第二层是演化引擎 AEGIS。它把演化形式化为操作镜像（operational mirror）：状态 s_t=(H_t,T_t)，T_t 是不断累积的轨迹库；候选 harness 由确定性接受算子决定是否采纳，并要满足跷跷板约束（seesaw constraint），即不得让任何已解决的任务退化。同一个元智能体（meta-agent，实验中为 Claude Opus 4.6）依次选择性地执行四个阶段，任一前置阶段判断信号不足都会让本轮空转。Digester 把每个任务的原始轨迹压缩成结构化摘要（是否通过、失败类别、涉及组件、证据摘录，以及跨轮历史），GAIA 上约 10M token 被压缩到约 10K；如果可行动性低于阈值 α，本轮直接退出，而 α 的取值论文未说明。Planner 构建调整全景（adaptation landscape），列出哪些任务在失败、试过什么、哪些修改类型还没试过，用来对抗探索不足。Evolver 以带类型的构建操作生成候选，每个候选附带变更清单（change manifest），写明改动、预期效果、预计解锁或可能受损的任务，以及上线后应在轨迹中出现的特征；如果涉及新代码，还必须实际运行验证。Critic 对照清单与轨迹证据评估候选，最多要求一次修订，然后给出排序，用来对抗奖励投机。最后由确定性门控（deterministic gate）依次检查清单完整性、配置规范化、构建与冒烟测试和跷跷板约束，用来对抗灾难性遗忘。作者的设计原则是 LLM 只负责提出方案，是否上线由规则决定；连续 P 轮没有采纳修改，演化就停止。对于异质任务，作者引入变体隔离（variant isolation）：最多维护 K 个变体，每个任务路由到历史成功率最高的变体（集成路由，ensemble routing）。一个修改如果改善部分任务、又让另一部分退化，就分叉成新变体，而不是直接被拒绝，跷跷板约束也改为按变体分别检查。作者认为，正是类型化组合让每次修改的作用范围变得明确，变体隔离才有可能成立。论文给出了一个具体例子：GAIA 上 Sonnet 4.6 的第 10 轮，Digester 发现所有维基百科抓取都返回 0 字符，Planner 指出工具类修改已经九轮没有上线，Evolver 提出新增调用 MediaWiki API 的 WikiTextFetch、加一行提示词、并恢复第 8 轮配置。该修改上线后成绩从 74.8% 升到 79.6%，预测的 7 个任务中有 5 个翻转为通过。第三层是协同演化（co-evolution）：每轮的轨迹写入一个先进先出的回放缓冲区（replay buffer），同一份数据既交给 AEGIS 修改 harness，也用于跨 harness 的组相对策略优化（GRPO）来更新模型权重。同一任务的轨迹不论来自哪个 harness 或哪个模型版本都归为一组，组内优势按 Â=(r−μ)/(σ+ε) 计算，目标函数带裁剪和 KL 项，每条轨迹在产生它的 harness 上下文下重新计算概率，因此不同版本的动作空间不需要对齐，也不需要额外的环境运行（rollout）。实验覆盖 GAIA（103 题）、ALFWorld（134 题）、WebShop（100 题）、τ³-Bench（3 个领域）和 SWE-bench Verified（55 题），task agent 为 Claude Sonnet 4.6、GPT-5.4 和 Qwen3.5-9B，最多演化 15 轮，指标为 pass@2，基线是不演化的 Static Harness 和单 agent 的 Claude Code SDK 演化器。结果是 15 个组合中 14 个提升，按峰值计算平均 +14.5%，最高 +44.0%（ALFWorld 上 Qwen3.5-9B 从 53.0% 升到 97.0%），起点越低提升越大；作者把这一现象解释为弱模型有更多可以由 harness 弥补的行为缺口，这是推测，没有经过验证。唯一没有提升的 GAIA·GPT-5.4 上，单一 harness 在第 4 轮达到峰值 73.8% 后跌到 49.5%，差距超过 ±8.5% 的置信区间；变体隔离则保持 87.4%，终值等于峰值，token 消耗也更少（107.8M 对 143.7M），这直接验证了按簇限定修改范围能防止跨簇遗忘。AEGIS 与 CC SDK 的准确率为 87.4% 对 86.4%，在误差范围内，只节省约 12% 的 token；作者把节省归因于 Digester 的压缩，并据此推断准确率主要来自类型化组件和结构化轨迹等基础设施，但这一归因没有单独消融 Digester。协同演化在 Qwen3.5-9B 上比只演化 harness 平均再提升 +4.7%（GAIA 从 37.4% 升到 41.7%，WebShop 从 49.0% 升到 54.0%）。案例分析证实三种病理都真实出现过：GAIA 在第 10 轮上线的修改中，部分任务靠利用 verifier 的格式规律过关，两轮内被识别并修复；τ³ Telecom 连续 5 轮追加同类规则后，第 7 轮下降 14.0 个百分点，第 9 轮恢复；ALFWorld 在第 4 至 7 轮只做局部提示词修改，命中率从 80% 降到 0%。这些下降说明，pass@2 的二值信号检测不到低于阈值的累积耦合，逐个修改的门控存在结构性盲区；SWE-bench 上 Qwen3.5-9B 各类修改的命中率只有约 0.05，说明模型能力存在下限。作者明确承认的局限包括：没有留出测试集，报告的是演化集上的峰值，存在选择偏差和过拟合；只测试了离散文本动作；meta-agent 是闭源模型，也没有评估更弱的 meta-agent；协同演化需要同时控制 harness 和模型训练；基准规模有限；操作镜像只是设计清单，不是有收敛保证的理论。根据论文设计还可以推断出几点潜在不足（并非作者原话）：变体隔离、架构对比和协同演化都只在单一设置上验证；协同演化缺少“只训练模型”的对照，因此“同时突破两个天花板”只验证了一半；论文没有报告多次重复运行的方差；task agent 的运行成本没有单独统计；算法 1 没有交代候选是在上线前还是上线后评估。总的来看，这篇论文证明的是：在固定任务集上、模型冻结的前提下，基于轨迹、带类型约束的 harness 演化能明显提高 pass@2 峰值，对较弱模型尤其如此，而任务异质时必须依靠变体隔离才能保持稳定。它给后续研究的启发是，可以把 harness 当作可学习的对象，并用强化学习的病理清单来设计防御；它的贡献边界在于，泛化到未见任务、其他 meta-agent 以及更广泛的协同演化，都还没有得到验证。
