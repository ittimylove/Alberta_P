## 0. 一句话

模型升级后，不再整轮重跑 harness 演化，而是用少量测试和轨迹信号判断旧 harness 的每一层该怎么处理：保留、删除、改接口、合并，或者只改步数和超时。前提是先弄清楚失配集中在哪几层，以及失配的原因。

### 0.1 一个具体例子：什么叫"模型升级后用旧 harness"

假设你用 DeepSeek V3.2（旧模型 M）搭了一个修代码的 agent。为了让它表现好，你调了 7 层：在 system prompt 里写好工作流程，把编辑工具做成 V3.2 用着顺手的格式，用 middleware 在提交前提醒它跑测试，在 memory 里记下它犯过的错，等等。

后来 DeepSeek 出了新版本（新模型 M′）。大多数人的做法是**只改配置里的模型名，其他都不动**，这就是"用旧 harness"。这是升级时的默认做法，不是本研究设计出来的。

问题在于，这 7 层是按 V3.2 的毛病调的。换了新模型以后，各层的处境可能不同：

| 处境 | 例子 |
|---|---|
| 还有用 | 正常 |
| 多余了 | 新模型自己就会跑测试，提醒只是白费 token |
| 开始添乱 | 编辑工具的格式不合新模型的习惯，报错变多 |
| 问题其实在步数和超时 | 新模型想得更久，被超时截断 |

打个比方：换了一个新司机，旧车上的倒车提醒、车道保持、限速器，哪些还需要，哪些多余，哪些反而碍事？

目前升级时只有两种做法：

1. **全部照旧**：不知道哪一层在拖后腿。
2. **整轮重新演化**：用 AHE、HarnessX 这类方法从头再优化一遍，成本高，而且说不清改了什么。

分诊程序走第三条路：**先查清每一层的状况，再只改有问题的层。**

### 0.2 分诊程序的输入和输出

**输入**

| 输入 | 说明 |
|---|---|
| 旧 harness H | 7 层代码和配置，每层都能单独开关 |
| 旧模型的历史记录 | 在 M 上调优时留下的轨迹，以及每层在 M 上的贡献 δₗ(M)。这些已经有了，不用重跑 |
| 新模型 M′ | 只需要能调用 API |
| 一小批题和评测器 | 例如从 SWE-bench Verified 抽 30 题 |
| 预算上限 | 最多跑多少次 |

**输出**

1. **逐层决策表**。下表的数字是虚构的，只用来说明格式：

| 层 | 判断 | 处理 | 依据 |
|---|---|---|---|
| system prompt | 正常 | 保留 | 新旧模型上的各项指标接近 |
| tool implementation | 接口失配 | 只改编辑工具的格式 | 新模型在这层的报错率从 3% 升到 18%；去掉这层反而涨分 |
| middleware（测试提醒） | 冗余 | 删除 | 新模型 95% 的题本来就会主动测试，去掉不掉分 |
| memory + middleware | 冲突 | 合并成一个 | 两层都触发重复验证，耗尽步数 |
| 步数 / 超时 | 操作点不合适 | 超时从 120s 改为 240s | 放宽后 8 道失败题中恢复了 5 道 |

2. **修改后的 harness H′**：按上表修改后的版本。
3. **一份短报告**：H′ 比"照旧"多挽回了多少损失，花了多少次运行和多少 token，有没有把原来能做对的题改坏。

**与整轮重新演化的区别**：两者的输入相同。重新演化只输出一个新的 H′，说不清哪层出了错、为什么这样改，成本也更高。分诊多输出一张决策表，说明为什么这样改。

### 0.3 两个容易混淆的地方

1. **研究和工具是两回事。** C1 研究先要回答三个问题：失配是否存在，出在哪几层，是哪种原因。这需要做较多实验（第 10 节）。分诊程序是研究做完后得到的工具，输入输出就是 0.2 节那两张表。
2. **"旧 harness"不等于坏东西。** 新模型配旧 harness，整体分数很可能仍然上升，因为新模型本身更强。问题在于其中有几层在拖后腿，被整体的上升掩盖了。分诊要找的就是这几层。

## 1. 最终目的

### 1.1 目标

做一套**模型升级分诊程序**：拿到新模型 M′ 后，判断旧 harness H 的每一层该怎么处理。

| 判断结果 | 处理方式 |
|---|---|
| 正常 | 保留 |
| 冗余 | 删除 |
| 接口失配 | 只重调这一层的接口 |
| 层间冲突 | 合并，或只保留一层 |
| 操作点不合适 | harness 不动，只改步数和超时 |

**成功标准**（两条都要满足）
1. 用明显低于整轮重新演化的成本，挽回大部分升级损失。
2. 在**没有参与设计的另一对模型**上同样有效。

**核心指标**

> 恢复率 = [acc(分诊后的 H, M′) − acc(旧 H, M′)] ÷ [acc(重新调优的 H, M′) − acc(旧 H, M′)]

与 token 成本、回归率一起报告。

### 1.2 三个层次的产出

| 层次 | 产出 | 单独拿出来的价值 |
|---|---|---|
| 0. 描述 | 失配是否存在，集中在哪几层 | 低，只是一个观察 |
| 1. 解释 | 失配属于四种机制中的哪一种 | 中：能回应"harness 可迁移"和"harness 是模型特异的"之间的争论 |
| **2. 处方** | **分诊程序，并在另一对模型上验证** | **高：直接改变升级时的做法** |

第 0、1 层是第 2 层的前提：不知道失配在哪里，就没有对象可以分诊；不知道是哪种机制，就不知道该删、该改还是该合并。

### 1.3 为什么值得做

- AHE 在引言里指出，换基座模型后 harness 需要重新适配，而人工适配跟不上模型更新的速度。[核实]（p.2）
- 现有的自动方案是整轮重跑。AHE 一轮约 32 小时，HarnessX 的 meta-agent 一次要 100M–175M token。[笔记] 重跑完也说不清旧 harness 错在哪里。
- 即使继续用自动演化，分诊结果也能告诉优化器"只改这两层"，从而缩小搜索范围。AHE 的自我归因几乎预测不到回归，precision 约 11%。[核实] 缩小改动范围可能降低回归风险。[判断]

## 2. 问题定义

- **对象**：旧模型 M，以及为它调好的 7 层 harness H。7 层是 system prompt、tool description、tool implementation、middleware、skill、sub-agent、long-term memory。H 有自己的操作点 θ（步数预算、超时）。
- **升级**：换成同一家族的新模型 M′，H 原样沿用。
- **层贡献**：δₗ(M) = acc(H, M) − acc(H 去掉第 l 层, M)。
- **失配**：如果 δₗ(M′) 明显小于 δₗ(M)，甚至变成负数，就说第 l 层失配。

**研究问题**：失配集中在哪几层？每层属于哪种机制？只修失配的层，能否挽回大部分损失？

## 3. 场景、缺口、后果

### 3.1 场景

每次模型升级都会碰到这个问题。AHE、Self-Harness、SSA 都把"换模型后 harness 需要重新适配"当作研究动机 [核实]，但本地 8 篇论文里没有一篇做过同家族"旧 harness + 新模型"的实验 [核实]。

### 3.2 缺口：现有工作漏掉的三件事

1. **参照点不对**。现有的迁移实验比的是"演化后的 harness"和"种子"，比种子好不等于没有失配。
   - 例：HarnessFix 修好的 harness 用在源模型上是 +18.4，迁移到其他模型只剩 +5.5~+9.5。[核实] 中间丢掉的 9~13 个点就是失配的代价，论文只报告了"仍为正"。
2. **只看整体，层与层之间的抵消被掩盖**。
   - AHE 在同一个模型上已经出现这种抵消：三个单组件增益合计 +11.1 pp，完整版只有 +7.3 pp；只加 system prompt 时是 −2.3 pp；在 Hard 档上，只加 memory 为 63.3%，完整版为 53.3%。[核实]
   - 换模型后，"整体为正"可能是"有的层在帮、有的层在拖"相加的结果。[判断]
3. **操作点和 harness 内容混在一起**。
   - AHE 自己承认，跨模型迁移的数字混杂了 harness 的可移植性和操作点耦合；同家族内，增益在不同推理档位之间也不单调：medium +2.3，high +7.3，xhigh +2.3。[核实]

### 3.3 后果：遗漏为什么会改变结果

- **学术结论可能要改写**。如果某几层在 M′ 上的贡献反号，LIFE 说的"与模型无关"、AHE 和 HarnessFix 的"迁移为正"，就要改成"整体为正，但掩盖了贡献反号的层"。[假设]
- **升级做法会变**。可以从"整体沿用"或"整体重跑"变成"只修一两层"或"只改操作点"。演化循环倾向于往 harness 里加东西，比如 AHE 的 tool 层增长到 1364 行 [笔记]，而 C1 可能会指出正确的做法是删层。[假设]
- **如果是负结果**：同家族升级几乎没有失配。这是"可迁移"一方的第一份直接证据，可以把 Self-Harness、SSA 的"模型特异"主张限定在跨家族的场景。

## 4. 四种失配机制

> 这四种机制是综合 AHE、SSA、LIFE 和 2605.30621 的证据归纳出来的，**不是文献中现成的分类**。[设想]
> 同一层可能同时存在多种机制；分类规则需要在试点阶段通过人工标注和一致性检查来校准。

| 机制 | 发生了什么 | SWE-bench 上的例子 | δ 的模式 | 轨迹信号 | 处理 | 依据 |
|---|---|---|---|---|---|---|
| **1. 冗余**（能力被吸收） | 这层原本用来弥补 M 的短板，M′ 自己已经会做 | middleware 提醒"提交前跑测试"，而 M′ 本来就会主动测试 | δₗ(M′) ≈ 0：去掉也不掉分，只是浪费 token | 这层的提醒或工具基本不触发，或者触发后行为不变 | 删除 | 2605.30621：强模型从 harness 受益更少 [摘要] |
| **2. 接口失配** | 功能还需要，但形式和 M′ 的习惯对不上 | 编辑工具按 M 的习惯设计，M′ 更习惯 apply_patch；定量提示让 M′ 发出空工具调用来凑数 | δₗ(M′) 变小或为负；按 M′ 重调接口后回升 | 这层相关的工具报错（SSA 的 R8 tool_invocation）、格式错误、拦截、重试增多 | 保留功能，重调接口 | SSA 的家族适配：GPT 用 apply_patch，Grok 用原子工具；定量提示在 Gemini、Grok 上导致空调用 [笔记] |
| **3. 层间冲突** | 每层单独看没问题，叠在一起互相干扰 | memory、middleware、system prompt 都要求收尾验证，造成重复复查，耗尽步数；升级后 M′ 自己也做验证，可能变成四重验证 | 单独去掉 A 或 B 都回升，同时去掉时回升不叠加（存在交互项） | 不同层触发相似的动作，重复检查占用的步数增加 | 合并，或只保留一层 | AHE：+11.1 vs +7.3；Hard 档 memory-only 63.3% vs 完整版 53.3%，作者归因于冗余复查 [核实] |
| **4. 操作点** | harness 内容没问题，是步数和超时按 M 的节奏设定 | M′ 思考更久、每步更慢，在超时处被截断 | 失配不集中在某一层；放宽步数和超时后差距明显缩小 | 失败集中在达到步数上限或超时 | 只重设操作点 | AHE：操作点按 GPT-5.4 high 拟合；xhigh 超时更多、增益反而更小 [核实] |

**判别顺序**
1. 先用"放宽操作点"这个条件排除机制 4。
2. 再看 δ 的方向，结合轨迹信号：
   - δ ≈ 0 且这层几乎不触发 → 冗余；
   - δ < 0 且这层有接口报错 → 失配；
   - 存在交互项 → 冲突。

**最难区分的一对**：冗余和天花板效应。M′ 本来就强时，"不需要这层"和"这层被吸收了"在数据上表现相同。对决策影响不大，结论都是"可以删"；但在论文里只能说"可以删"，不能说成"被吸收"的因果。

**与 LIFE 失败分类的关系**：LIFE 分析的是**单个模型的失败**，分为动作实现、环境契约、轨迹退化、一般推理四类 [笔记]。本文分析的是**升级前后 harness 作用的变化**。两者有对应关系（接口失配大致对应 LIFE 的动作实现和契约失配），但不能直接套用。

## 5. 前置步骤：在 M 上把 H 调好

### 5.1 "调好"的三个必要条件

1. **H 在 M 上明显优于种子 H₀**。否则 H 不值得沿用，也就谈不上失配。
2. **每层在 M 上都有正贡献**，即 δₗ(M) > 0。在 M 上本来就没用的层，升级后没用也说明不了问题。这与 AHE 的"最小种子"原则一致 [核实]（§3.1）。
3. **调优过程可以复现**。预算、规则和每次修改都要有记录，以应对"失配只是你调的方式造成的"这类质疑。

### 5.2 流程：限定范围、有门控的迭代调优 [设想]

1. **切分数据**：从 SWE-bench Verified 中分出调优集（如 30 题）和评测集（另外 20–50 题），两者不重叠。这是为了避免 AHE、HarnessX 那种在同一题集上演化又报告结果的问题。
2. **从最小种子 H₀ 出发**：一个 shell 工具加一段简短的 system prompt，其余层关闭。
3. **逐轮迭代**：
   1. 用当前 H 在调优集上跑 M，每题 k=2–3 次；
   2. 阅读 M 的失败轨迹（可以由你阅读，也可以由 coding agent 阅读、你来把关）；
   3. 每轮最多改一到两层，每处修改都写记录：针对哪类失败、改了哪一层、预期修好哪些题；
   4. 用门控决定是否接受：调优集通过数不降，且至少一项上升，否则回滚。这借鉴 Self-Harness 的接受条件 [笔记]，只借规则，不复现它的系统。
4. **停止**：连续 2 轮没有修改被接受，或预算用完（如 6 轮）。
5. **最终检查**：对 H 做逐层消融，确认每层的 δₗ(M) > 0。为 0 或负的层，要么删除，要么在论文中如实说明。

### 5.3 7 层在 SWE-bench 上可以调什么（示例）

| 层 | 可调内容 |
|---|---|
| system prompt | 工作流（复现 → 定位 → 修改 → 测试）、提交规范 |
| tool description | 参数说明和示例的措辞 |
| tool implementation | 编辑语义（锚定上下文替换、修改后返回 diff）、长输出截断、超时时返回部分输出、结构化报错。参考 SSA 的做法 [笔记] |
| middleware | 循环检测、剩余步数提醒、上下文压缩、提交前检查是否跑过测试 |
| skill | 例如"django 测试怎么跑""怎么写复现脚本" |
| sub-agent | 例如专门写复现测试的子 agent、提交前审查的子 agent |
| long-term memory | 从调优集失败中总结出的跨任务教训 |

### 5.4 风险

- **成本**：约 6 轮 × 30 题 × k=2 ≈ 360 次运行（只跑 M），需要先按模型单价估算费用。
- **"人造 harness"的质疑**：补一个外部对照，例如 mini-swe-agent 这类社区 harness，检查结论的方向是否一致。
- **信息泄漏**：调优过程中**不能使用 M′ 的轨迹**。如果由 frontier 模型帮你读轨迹，这个选择要在整个研究中固定并写明。
- **可能的捷径**（待核实）：SSA 在同一个共享 harness 下跑过同家族多代模型，如 Sonnet 4.0/4.5/4.6、Qwen3-Coder → Qwen3.6 [笔记]。代码已开源，但原文没有说明轨迹数据是否公开 [笔记]。如果能拿到，可以先用这些轨迹预检同家族各代之间的报错率和超时率变化。不过 SSA 是按家族调的，不是按版本调的，只能作为预检，不能替代 5.2。

## 6. 分诊程序 [设想]

### 6.0 前提：层级埋点

harness 中每个事件都要记录**它来自哪一层**：提示注入、工具调用、middleware 拦截、memory 读取、skill 加载、子 agent 调用。思路与 HarnessFix 把运行时步骤映射回实现位置相同 [笔记]。你的 harness 是自建的，可以直接在代码里打标签，不需要事后推断。

M 上调优时的轨迹和逐层的 δₗ(M) 全部保存，作为旧模型的基线，之后不用重跑。

### 6.1 五个步骤（越往后成本越高）

**A. 挑出有区分度的题**（少量测试）
- 用旧 H 在调优集上跑 M′，每题 k=2；M 在这些题上的结果已经有了。
- 按 M、M′ 的结果分四类：

| 类别 | 用途 |
|---|---|
| 两边都做出来 | 跳过 |
| 两边都做不出来 | 跳过（多半是能力上限） |
| **M 能做出来、M′ 做不出来** | **主样本** |
| M′ 能做出来、M 做不出来 | 对照，检查某层是否在帮 M′ |

- 后续所有测试都只在主样本上做。这是成本能降下来的主要原因。

**B. 先排除操作点**（1 个配置）
- 只放宽步数和超时（例如加倍），在主样本上重跑。
- 如果大部分题恢复，判为"只改操作点"，**到此结束**。

**C. 用轨迹信号给每层打初步标签**（不需要额外运行）

| 信号（逐层比较 M′ 与 M） | 指向 |
|---|---|
| 几乎不触发，或者触发前后下一步动作相同 | 冗余 |
| 这层相关的工具报错、格式错误、拦截、重试比例明显升高 | 接口失配 |
| 不同层触发相似动作，占用步数的比例明显升高 | 冲突（标出嫌疑层对） |
| 各项指标与 M 接近 | 正常 |

输出：每层的初步标签，以及 2–3 个可疑层。

**D. 只对可疑层做确认测试**（少量测试）
- 只在主样本上，对可疑层做"逐层去掉"，对嫌疑层对补测"同时去掉"。
- 可疑层较多时（≥4），用 Plackett–Burman 这类筛选设计：8 个配置可以估计 7 个主效应，代价是交互项与主效应混杂，需要时再补测拆开。
- 每个配置边跑边看，结论清楚就停（序贯检验，如 SPRT）。
- 用 D 的结果核对 C 的标签：一致就采纳；不一致以 D 为准，并把这个案例记录下来，用于修订 C 的规则。

**E. 按机制做限定范围的修改，然后验收**
- 冗余 → 删除；接口失配 → 只改这一层的描述或实现，最多改几处，每处都过门控；冲突 → 合并或只保留一层。
- 门控：通过数不降且至少一项上升 [笔记，Self-Harness]；同时不破坏原本能做出的题 [笔记，HarnessX 的 seesaw 约束]。
- 在评测集上与"旧 H 原样沿用"做比较。

**产出**：逐层决策表，每行附上轨迹证据和确认测试的数字。

### 6.2 更省、但工程风险较高的做法

对"M 能做出来、M′ 做不出来"的题，不从头重跑，而是从新旧轨迹开始分叉的那一步接着跑，只切换可疑层。这需要能把 SWE-bench 的仓库状态恢复到那一步（例如重放之前的工具调用）。可行的话，D 的成本还能大幅降低。**目前还没有确认在你的环境里是否可行**。

### 6.3 哪些是现成方法，哪些是设想

- **现成的方法**：
  - 筛选设计（Plackett–Burman、部分析因）、序贯检验（SPRT），都是经典的实验设计和统计方法；
  - 把失败映射到层：HarnessFix；
  - 接口报错信号：SSA；
  - 修改门控：Self-Harness、HarnessX。
- **设想**：把这些组合成五步程序、C 中的判别规则、下面的运行次数估算。这些都需要在第一对模型上校准。

## 7. 怎么证明分诊程序有用

### 7.1 对照组

| 对照 | 回答什么 |
|---|---|
| 旧 H 原样沿用 | 什么都不做的下限 |
| 只重设操作点 | 最简单的修改够不够 |
| **随机选层，用同样的预算做限定修改** | **轨迹信号是否真的有用。这是最关键的对照，没有它就说不清是信号选对了层，还是改哪层都会涨** |
| 在 M′ 上跑轻量的重新调优循环（流程同 5.2） | 真正的对手，同时提供恢复率的分母 |
| 分诊程序 | 本方法 |

### 7.2 判断准确率

在第一对模型上额外做一次完整的逐层消融（9 个配置：H、H₀、逐层去掉 7 个），得到每层的"真实标签"。然后统计分诊程序对每种处理方式判对多少、漏掉多少。这一步只在研究阶段做，实际使用时不需要。

### 7.3 留出验证

- 规则在第一对模型上定稿后冻结，再用于**第二对模型**，最好再加一对不同家族的模型。
- 如果规则换一对模型就失效，说明它只是拟合了第一对模型。

### 7.4 指标

- 恢复率（见 1.1）
- 每挽回 1 个百分点所花的 token
- 回归率：原本能做出、修改后做不出的题所占的比例

## 8. 成本：坦白地说能省多少

粗略估算（30 题调优集）[设想]：

| 阶段 | 运行次数 |
|---|---|
| A 挑题 | 约 60 |
| B 操作点 | 约 30 |
| C 轨迹打标签 | 0 |
| D 确认测试（3 个可疑层） | 约 90 |
| E 修改与门控 | 约 40 |
| **合计** | **约 220** |

对比：

- **相对重量级演化**（frontier meta-agent，一次 100M–175M token [笔记]）：节省很多。
- **相对轻量的重新调优**（约 360 次）：只省约 40%。这时分诊的卖点不在省钱，而在：
  1. 知道每层为什么这样处理；
  2. 只改有证据的层，回归风险可能更低 [判断]；
  3. 决策表可以积累，下次升级时直接对照。

如果实验显示轻量重调同样便宜、同样好，课题定位要从"更便宜"改成"同样成本下更可靠、更可解释"。

## 10. 下一步，以及继续、调整、放弃的依据

### 第 0 步（约 1 天）
- 读 2609.20804、2610.00917 的正文，以及 ModularRSI（2609.14857）的正文。
- 确认同家族前后两代便宜模型的可得性和价格。

**判断**：如果正文中已有同家族新旧对比，并且做了组件级分析 → **放弃**，或者把课题调整为"扩展到 7 层 + 分诊"。

### 第 1 步：存在性试点（约 2 周）
1. 从 SWE-bench Verified 抽 20 题。
2. 按第 5 节在 M 上调好 H。
3. 跑 4 组条件，每题 k=3：M 上的 H、H₀；M′ 上的 H、H₀、H + 按 M′ 重设的操作点。
4. 计算增益 G(M) = acc(H, M) − acc(H₀, M) 和 G(M′)，并估计运行间的标准差 σ。

| 结果 | 结论 | 决策 |
|---|---|---|
| G(M′) 比 G(M) 低 2σ 以上，且重设操作点挽回不到一半 | 失配存在，来自 harness 内容 | **继续**：进入第 2 步 |
| 重设操作点挽回一半以上 | 失配主要来自操作点 | **调整**：课题缩小为"操作点混杂" |
| 差距在 2σ 以内 | 反例成立，或噪声太大 | 换更难、区分度更高的子集再试一次；仍然没有差距 → **放弃** |

> 2σ 和"挽回一半"是初始阈值，不来自文献。试点测出实际方差后可以调整。

### 第 2 步：解释层（第一对模型）
- 做完整的逐层消融（9 个配置），并在 M′ 上跑一次轻量的重新调优，得到恢复率的分母。
- 用轨迹把每层归到四种机制之一，得到"真实标签"。

### 第 3 步：处方层
- 按第 6 节运行分诊程序，与 7.1 的所有对照组比较。
- 冻结规则，用于第二对模型（以及一对跨家族的模型）。

**放弃条件**（满足任一条，就把课题收缩为第 1 层"解释"）
1. 在第一对模型上，分诊的判断准确率不比随机选层高。
2. 换到第二对模型后，恢复率明显下降。
3. 轻量重调在同等成本下恢复率更高，并且回归率不比分诊差。

## 11. 延伸方向：升级前预测哪些条目会过时（2026-10-20 检索）

### 11.1 想法

harness 中的每条规则可以分成两类：

- **环境结构**：任务和环境本身的要求，换什么模型都需要。
- **模型补丁**：弥补某个模型自身的缺陷，换模型后可能过时。

在 M 上调优时，每处修改都留有记录，写明它针对哪类失败（见 5.2 节）。据此提出：**在跑新模型之前，只根据这些"为什么加这条"的记录，预测每条规则升级后是否会过时；再用同家族升级实验检验预测准不准。**

注意：环境结构和模型补丁是按**条目**划分的，不是按层。同一层可以同时包含两类，所以埋点要细到每条规则。

### 11.2 最接近的工作：Ecdysis（2609.11677），已读正文（经工具摘要）

| 项目 | Ecdysis 做了什么 |
|---|---|
| 逐条分类 | **做了。** 把每个独立的修改决策标为 **MSA**（model-specific accommodation，迁就当前模型的修改）或 **HLR**（harness-level repair，修复运行时机制本身的错误）。MSA 基本对应本文的"模型补丁"，HLR 基本对应"环境结构"（附录 A） |
| 标签怎么来的 | **事后人工审计**：5 名专家独立标注，多数投票决定。伦理声明写明专家都是论文作者 |
| 测了什么 | MSA 比例：SE 基线 60.00%，Ecdysis 无 FDCR 75.61%，有 FDCR 45.45%。三个数据集合并统计（τ²-Retail、τ²-Airline、AgentBench） |
| 跨模型迁移 | 在 Qwen3-8B 上演化出 harness，直接用到 Qwen3-14B、Qwen3-32B、MiniMax-M2.7、Llama-3.1-8B 上。同家族只比了**规模**（8B→14B/32B），**没有新旧版本对** |
| 逐条预测 | **没有。** 标签是事后判断；演化时用"失败是否在多个任务中反复出现"和 FDCR 作为启发式，让修改偏向 HLR，但不对单条修改做迁移预测 |
| 作者承认的局限 | 只能减少 MSA，不能消除；"单靠是否反复出现，可能放大反复出现的模型特异失败"（§7） |

### 11.3 其他相关工作

- **One Recipe, Many Harnesses**（2608.10178）[摘要]：把演化出的 harness 解释为补偿层，同时补偿编程语言生态和模型行为缺口。拆分的维度是编程语言，不是模型版本。
- **SHarP**（2610.04178）[摘要]：针对当前模型逐模块消融，把冗余模块剪掉。不涉及换模型。
- **Harness Annealing、EvoIn、EvoHarness-RL** [TLDR]：通过训练把 harness 的作用内化进权重，路线是训练，不是预测。
- **业界博客** [只看到搜索摘录]：nat.io《The Agent Harness Has a Half-Life》、Addy Osmani《Agent Harness Engineering》、MindStudio。这些文章主张把 harness 组件当作"关于模型局限的假设"，给它们标上版本和过期条件。属于实践建议，没有实证。

### 11.4 结论：还剩什么空白

**已有，不能算创新**
- "harness 里有一部分在迁就特定模型"这个概念，以及逐条分类的做法（Ecdysis 的 MSA/HLR）。
- "组件会过期"的说法（业界博客）。

**在本轮检索范围内没有找到**
1. **事前预测**：在跑新模型之前，根据调优记录逐条预测是否会过时。Ecdysis 的标签是事后人工判断。
2. **逐条检验**：Ecdysis 默认 MSA 迁移得更差，但正文中没有看到它把每条修改的 MSA/HLR 标签和这条修改的迁移结果一一对应来验证（依据工具摘要，未逐页核对）。也就是说，"MSA 会过时"这一前提本身还没有被直接检验过。
3. **新旧版本升级**：Ecdysis 只比较了同家族的不同规模，没有比较同家族的新旧版本。

**置信度：中**（高于上一轮）。Ecdysis 的正文已读，但读的是工具摘要，没有逐页核对；博客原文没有打开。

### 11.5 对 C1 的影响

- **术语对齐**：文中直接引用 Ecdysis 的 MSA/HLR，说明"模型补丁 ≈ MSA，环境结构 ≈ HLR"，不另起新词。
- **创新点改写**：从"发现模型补丁"改为"**检验 MSA 标签能否预测逐条的升级结果，以及能否在升级前自动给出这个标签**"。
- **必须加的对照**：
  1. Ecdysis 式的"是否跨任务反复出现"作为预测器；
  2. 人工 MSA/HLR 标签作为预测器；
  3. 本文的"添加原因"自动预测器。

  三者比较逐条预测过时的准确率。
- **可以借用的反例**：Ecdysis 自己承认"单靠是否反复出现，可能放大反复出现的模型特异失败"。这正好说明需要一个比"是否反复出现"更好的判断依据。

  - 分诊程序优于随机选层，并且能迁移到第二对模型
