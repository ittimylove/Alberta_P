## 1. 场景与输入

| 问题 | 回答 | 原文依据 |
|---|---|---|
| 适用于什么情况 | 作者预期该方法基本与领域无关，适用于“任何语言模型被任务特定 harness 包裹”的场景。 | p.24：“we expect it to apply in any setting where a language model is wrapped by a task-specific harness.” |
| 已验证的场景 | 在线文本分类、检索增强的数学推理、智能体编码（TerminalBench-2）。 | p.5 第 4 节 |
| 前提条件 | 需要搜索集（用于评估候选并产生反馈信号）和任务奖励函数；需要能力较强的编码智能体作为 proposer（作者认为该工作流约在 2026 年初才变得可行）；需要一份 skill 文本来说明目录结构、可改与不可改的文件等。 | p.4；p.4 脚注 1；p.5；p.24 |
| 搜索集要求 | 搜索集应对基线有难度，规模以每次运行能做约 50 次完整评估为宜（分类实验 50–100 个样本，数学检索 88 题）。 | p.24–25（附录 D，作者注明这是工程经验，不是科学结论） |
| 能看到哪些轨迹 | 每个已评估 harness 的目录中包含：源代码、分数、执行轨迹（提示、工具调用、模型输出、状态更新）。此外还会存储 proposer 自己的推理轨迹（Figure 2：“proposed code, reasoning traces, evaluation scores”）。 | p.4；Figure 2（p.2） |
| 能看到多大范围的历史 | **所有**历史候选，没有父代选择规则。实测每次迭代读取 82 个文件（中位数，范围 69–99），会引用 20 个以上的历史候选。 | p.4；p.2；Table 8（p.15） |
| 访问方式 | 通过 grep、cat 等终端工具按需检索，而不是作为单个提示整体输入。 | p.4 |
| 不能看到什么 | 测试集结果。 | p.4：“The proposer never sees test-set results” |
| 其他可接入的信息 | 作者建议把已有的离线经验（其他模型的 rollout、已解题语料、相关论文）转换成相同的目录结构以便热启动。实验中观察到 proposer 引用了另一次早期搜索运行的结果。 | p.25；p.17（Iteration 10） |
| 反馈中是否包含人工标注的失败原因 | 未说明 | — |

## 2. 修改对象

| 对象 | 是否修改 | 原文依据 |
|---|---|---|
| 整个 harness | **是**。每个 harness 是单文件 Python 程序，proposer 可以做局部编辑或较大规模重写，修改范围覆盖“从检索、记忆、提示构建逻辑到完整程序重写”。 | p.4：“whether to make a local edit or a more substantial rewrite”；p.5 |
| Prompt | 是（作为 harness 的一部分）。例如 TerminalBench-2 早期迭代修改了 prompt 模板，结果导致回归。 | p.5；附录 A.2（p.16） |
| 控制逻辑 / 控制流 | 是。例如修改完成确认流程（completion flow）和观测处理、加入循环中断机制；文本分类中出现 draft→verification 两次调用的控制流；数学中出现四路由。 | 附录 A.2（p.16–17）；附录 B（p.17–21） |
| 检索 / 记忆策略 | 是。例如 TF-IDF 检索、对比样本对、BM25 路由与重排。 | 附录 B.1–B.2（p.18–21） |
| 新增组件 | 是。TerminalBench-2 的最优改动是纯增量式的“环境快照引导”，在 Terminus-KIRA 基础上约增加 80 行代码。 | p.17；附录 B.3（p.21） |
| Skill | proposer 由人工编写的 skill 引导；原文说的是由人来“迭代 skill 文本”。**proposer 是否修改 skill：未说明。** | p.5；p.24 |
| 模型权重 | 否，底层模型冻结。同时修改权重被列为未来工作。 | p.5：“always frozen”；p.10 |
| 外循环 / 评估代码 | proposer 不负责运行评估，评估由独立程序完成。proposer 是否会修改外循环代码：未说明。 | p.25：“Automate evaluation outside the proposer.” |

## 4. 成功标准

| 问题 | 回答 | 原文依据 |
|---|---|---|
| 选择候选的标准 | 只按**搜索集整体表现**选择；多目标时（准确率 vs 上下文成本）取 Pareto 前沿。 | p.4；p.6；p.17：“selected solely by whether they improve search-set performance” |
| 最终评估 | 文本分类和数学：在留出的测试集上评估。TerminalBench-2：搜索和评估使用同一组 89 个任务。 | p.6；p.8；p.9 |
| 是否针对“修好原来的失败” | 方法层面没有以“修复特定失败案例”作为成功标准。TerminalBench-2 的逐任务分析显示，相对 Terminus-KIRA，在 89 个任务中的 7 个上有提升（protein-assembly、path-tracing 提升最大）。 | p.4；附录 B.3（p.21） |
| 对其他任务是否有效 | 文本分类：在 9 个未见数据集上平均 73.1%，高于 ACE 的 70.2%，6/9 个数据集最高。数学：一个 harness 在 5 个模型上相对无检索均有提升，平均 +4.7。 | Table 5（p.8）；Table 6（p.8） |
| 有没有回归——搜索过程中 | **有**。TerminalBench-2 的前 6 次迭代全部相对 64.4% 的基线回归（例如 58.9%（-5.6pp）、57.8%（-6.7pp）、63.3%（-1.1pp））；第 7 次迭代才得到最优候选。回归的候选不会被选中。 | 附录 A.2（p.16–17） |
| 有没有回归——最终 harness 相对基线 | 部分数据集和模型上不是最优，例如：USPTO 14.0，低于 ACE 的 16.0（Table 2）；OOD 中 FiNER 67.0 低于 ACE 的 74.0，FPB 94.0 低于 ACE 的 96.7，Bank77 82.7 低于 Few-shot(32) 的 86.0（Table 5）；数学中 Gemini-3-Flash 上 46.3，低于 Dense k=5 的 47.2 和 BM25 的 46.6（Table 6）。相对无检索基线，数学 5 个模型上没有回归；作者强调它避免了 dense retrieval 和 random few-shot 在部分模型上出现的性能倒退。 | Table 2（p.6）；Table 5（p.8）；Table 6（p.8） |
| 是否逐任务检查“原本通过的任务是否失败” | TerminalBench-2 只报告了提升的 7 个任务，**下降的任务数量未说明**。proposer 在提出第 7 次迭代时的设想是“不在已通过任务上冒回归风险”，但这是 proposer 的假设，原文没有给出验证。 | p.21；p.17 |
| 防过拟合检查 | 作者主张：代码空间中的过拟合（例如脆弱的 if 链、硬编码的类别映射）可以通过人工检查发现。TerminalBench-2 做了人工检查和正则审计，排查任务特定字符串是否泄漏。 | p.10；p.9 |
| 统计显著性 | 未说明 | — |
