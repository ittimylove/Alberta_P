## 对话过程

### 1. 结构化提取论文要点
- 用户要求只根据论文提取 8 项内容，并标注页码和段落。
- 产出 `SSA文章总结.md`。研究局限分成两部分：作者自己承认的（8.1–8.12），以及原文中的不一致和“未说明”事项（8.13–8.20）。
- 发现原文三处不一致：
  - 配置数量：§5.1 写 71 个，附录 C 写 63 个（3 个基准 × 21）。
  - 正文称 SSA 优于常用的开源 harness，但正文和附录都没有对比数据。
  - 交叉验证引用了 R9 标签，表 4 只定义了 R1–R8。

### 2. 摘要讲解
- 分五组：动机 → 核心概念 → SSA 方法 → 贡献一（分数）→ 贡献二（轨迹）。
- 核心概念 **intent-execution gap** 是双向的：模型 → 环境（执行是否忠实），环境 → 模型（反馈是否如实）。
- 摘要说“两项贡献”，引言列了四项，后者另含 solution distance 指标和 SWE-Pro 的 git 泄露。

### 3. Introduction 逐段讲解
- 逻辑链：harness 的定义 → 没有对齐时强模型也显不出优势（acc(H, M_A) ≈ acc(H, M_B)，只是非正式的说法）→ 定义双向鸿沟 → 图 1 的 gpt-oss 案例 → 反对针对单个模型调优，主张“不变原则 + 按家族适配” → 两个核心问题 → 四项贡献。
- 发现的问题：
  - 正文说解析错误“剥掉参数”，图 1 画的是“工具名被污染”。附录 G.1 说明两种情况都存在，并不矛盾。
  - 贡献 3 称行为签名“跨基准稳定”，但 Gemini 3.1 Pro 的回退率在 SWE-Verified 上是 14.3%，在 SWE-Pro 上是 1.7%。
  - 贡献 1 称所有模型都达标，§5.2 自己指出了 GPT-5.2-codex 这个例外。

### 4. 讨论：为什么不一开始就根据模型差异修改 harness？
- **原文有回答的部分**：单个模型的优化很脆弱，所以只在家族层面做有限适配（p.3，p.8）。已有的适配来自非正式观察（“we found”、日志），不是来自 §4/§5.3 的轨迹分析。
- **原文没有回答的部分**：没有“轨迹分析 → 修改 harness → 再评测”的闭环，作者只在结论里说轨迹分析“使协同设计成为可能”（p.14）。
- 【推断】solution distance 依赖全部运行结果构建答案库，只能事后计算。共享 harness 客观上起到了控制变量的作用。回退率和解决率无关，说明轨迹上的差异不一定是需要修的缺陷。

### 5. §2 SSA 架构
- 六个部件：任务、prompt、模型、工具、环境、hooks。核心是一个四步循环：调用模型 → 执行工具 → 追加结果 → 重复。
- 统一的模型接口把各家 API 转成七类事件，所有模型共用同一个 event loop。
- 一共 15 个工具，每个模型通常只用两个（bash + 编辑器），不同家族绑定的工具不同。
- 值得留意：
  - DropUnknownTool 是“悄悄丢弃”还是“丢弃并告知模型”，原文没有说明；这与 intent-execution gap 的主张存在张力。
  - 上下文裁剪的具体规则没有说明。
  - 这一节只有描述，没有和其他 harness 的架构做对比。

### 6. 用户提出候选问题
- 用户的假设：模型升级后，用“新模型的失败轨迹 + 旧模型配旧 harness 的成功轨迹”做对比来修改 harness。附带的 bug：怎样判断失败是 harness 造成的？
- 产出 `候选问题.md`，内容包括支持证据、风险（成功轨迹不等于正确接口，修改应针对接口而不是风格）、归因信号（R8 真实工具错误、缓存命中率、空调用、5 次复现）、混杂因素（评测环境问题、git 泄露、基础设施）。

### 7. 与 HarnessX 候选问题的区别
- 场景相同，研究的变量不同：**HarnessX 问题 1 研究“谁当医生”（meta-agent 用新模型还是旧模型），SSA 问题 1 研究“拿什么做诊断、什么时候该开药”（输入数据与失败归因）。**两者正交，可以单独成立，也可以组合。
- 核对了 HarnessX 原文：`task_history.jsonl` 是逐题记录，不是完整轨迹（p.43）。HarnessX 问题 1 条件 D 所说的“演化历史”不包含原始轨迹，所以没有覆盖 SSA 问题 1。运行目录里存有 `R<n>/trajectories/`（原始 rollout），可以作为两个问题的接口。
- 修改了 `候选问题.md`：改标题，新增 1.8 节，并建议一个组合实验条件 D′。

### 8. §3 SSA Refinements
- 第一次讲解太细，用户没看懂，于是改用主线式讲法重讲。
- **一句话：SSA 做了三件事，让模型和 harness 之间“不说错话、不听错话”。**
  - 3.1 把话说清楚（所有模型相同）：返回五项执行信息，长输出截掉中间、保留首尾；编辑遇到多处匹配就拒绝，成功后返回 diff。
  - 3.2 调节“想”和“做”的比例（按家族区分）：Claude 用定量提示（“调用工具 100 次以上”），Gemini/Grok 用模糊提示，否则它们会发出空调用来凑数。
  - 3.3 工具要顺手（按家族区分）：GPT 用 apply_patch；Grok 用拆分后的小工具，并关闭行号。
- 三项改进都没有消融实验。
- 其他发现：Grok 的 `file_write` 真实错误率约 44%（p.36），说明顺应偏好又带来了新的接口错位；Claude 在 SWE-Pro 上的 prompt tag 可能不含定量提示（需要对照 PDF p.75–76 核对）。

### 9. §4 Solution distance
- **一句话：一把“尺子”，在每一步量一量 agent 离正确答案还有多远。**
- D = 1 − 已写对的比例，在所有正确答案中取最接近的那个。D 下降表示在接近答案，D 上升表示回退。
- 三个设计：比较的是改动的行（纯文本）；正确答案可以有多个；多写的内容不扣分。
- 正确答案库来自本次实验中所有做对的运行（每道题 105 次尝试）。
- 局限：只比文字不懂语义、答案库不全、难题上答案库很薄。【推断】D = 0 不等于测试通过，而且这把尺子只能事后使用。

### 10. 实验设计解析
- 本质上是一次大规模观察性研究：21 个模型 × 3 个基准 × 5 次，得到约 138k 条轨迹。在此基础上做了五组实验：基准评测、轨迹分析、TB2 基础设施、git 泄露、gpt-oss 个案。
- 做得好的地方：规模大、harness 受控、主动审查评测本身、配置全部公开。
- 薄弱的地方：
  - 比较对象只是模型卡数字，没有对照组。
  - 没有消融实验。
  - 家族适配是怎么定下来的没有说明。
  - SWE-Pro 主表用的是有泄露的 Base 容器。
  - 置信区间把同一道题的 5 次运行当作独立样本。
  - judge 未验证，而且 judge 本身就是被研究的模型之一。
  - 答案库来自被评测的运行本身。
- **重要发现（需要核对 PDF p.73 表 11）**：Qwen3-Coder Next 在 SWE-Pro 上 Base 为 57.75%，Sanitized 为 43.39%，相差约 14 个点，远大于贡献 4 中“最多虚高 6.9%”的说法。

### 11. Table 3（TB2）解析
- PDF 文本抽取后表格错位，改为把 p.11 渲染成图片读取原表，数据已核对。
- 与模型卡比较：没有一个官方数字高于 SSA 区间的上限，“复现”成立。但其中 5 个模型的 SSA 点估计**低于**官方数字（低 1.8–3.3 个点），只是因为区间有 ±4 才算在区间内。Gemini 3 Flash 比官方高 16 个点，原因原文没有解释。
- 去掉限制后的提升在 0.67–11.91 个点之间，平均约 5.6。约一半模型低于原文所说的“5–10”。【推断】较弱的模型提升很少。
- 有限制条件下前四名（GPT-5.3、Opus 4.6、GPT-5.4、Gemini 3.1 Pro）相差不到 3 个点，在统计上分不出高低。

### 12. Figure 5 解析
- 2 × 2 布局：Opus 4.6 和 GPT-5.4，各在 SWE-Verified 和 SWE-Pro 上。三条线分别是改源码、临时测试、项目测试套件的比例。三条线加起来不等于 1，剩下的部分是探索活动。
- Opus 很早开始测试，后段大量跑项目测试；GPT-5.4 以临时脚本为主，项目测试较少。题目变难时，两者都是编辑增加、测试减少。
- 需要注意：
  - 成功和失败的运行混在一起算平均；进度被拉伸到 0–1，看不出轨迹的绝对长度。
  - 统计的是调用次数，不是工作量：apply_patch 一次能改多处；Claude 先写文件再运行，GPT 一条命令完成，这可能系统性抬高 Opus 的临时测试比例。【推断】因此“模型签名”中有一部分可能是 harness 接口的签名。

## 贯穿全程的关键判断

1. **主结论的边界**：“对齐的简单 harness 能跑出官方分数”是与模型卡数字比较得出的，没有对照组，也没有消融实验。它证明的是“能达到”，不是“更好”，也没有说明“为什么”。
2. **最扎实的部分**：SWE-Pro 的 git 泄露审计（Base 与 Sanitized 对照），以及 gpt-oss 的修复案例（42% → 64.64%）。
3. **最值得追问的地方**：
   - 轨迹分析与 harness 设计没有形成闭环（这正是候选问题 1 的切入点）。
   - Qwen3-Coder Next 在 SWE-Pro 上的分数可能被泄露严重抬高。
   - 行为签名中有多少来自模型本身，有多少来自工具接口和计数方式。
   - TB2 上“复现”的判定依赖较宽的置信区间。
