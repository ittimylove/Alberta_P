# 候选问题

**来源论文**：*Dissecting model behavior through agent trajectories*（Gupta et al., AWS AI Labs, arXiv:2606.17454v2）
**方法名**：SSA（Simple Strands Agent）
**记录日期**：2026-10-16

> 标注约定：带页码的内容出自论文原文；标【假设】的是待检验的猜想；标【推断】的是根据论文内容做的推理，论文本身没有给出结论；标【建议】的是操作方案，论文里没有。

## 问题 1：模型升级后，先判断失败是否由 harness 造成，再用新旧轨迹对比定位修改点，效果会不会更好？

### 1.1 一句话问题

【假设】模型升级时，旧模型有一套为它适配好的旧 harness，新模型直接沿用这套 harness 会不适配。如果“新模型 + 旧 harness”运行出了问题，那么拿**新模型的失败轨迹**和**旧模型 + 旧 harness 的成功轨迹**做对比，再据此修改 harness，效果会不会好很多？

**附带的 bug**：什么时候该拿旧模型来对比？新模型失败不一定都是 harness 不适配造成的。

### 1.2 现有工作的空白

论文**没有做过**这个实验，所以从原文里得不出“效果会不会好很多”的答案。作者只说轨迹分析“使协同设计成为可能”，并没有做“轨迹分析 → 修改 harness → 再评测”的闭环（p.14，§6 第 2 段：“understanding trajectory behavior is what makes model-harness co-design possible”）。

### 1.3 支持这个思路的证据

| 证据 | 原文依据 |
|---|---|
| 换模型后，旧的优化确实可能失效 | p.3，§1 “Problem-specific tunings…”段：“optimizations that overfit one model's quirks can degrade on the next” |
| 对 Claude 有效的定量 nudge 用到 Gemini/Grok 上，它们会发出空的工具调用来凑数 | p.5，§3.2 第 3 段 |
| harness 导致的失败可以很严重，修好后提升也很大：gpt-oss-120b 只修了服务端解析，pass@1 就从 42% 升到 64.64% | p.103，附录 G 第 1 段；p.106，§G.4 |
| “拿成功轨迹当参照”已有类似做法：solution distance 的经验解集就是用其他模型的 resolved 运行构造的 | p.22，§A.1.3 *The empirical solution subset* 段 |

【推断】这个方案相当于把“旧模型 + 旧 harness 的成功轨迹”当作参照，找出新模型从哪一步开始偏离。D(t) 正好可以逐步定位这个偏离点。

### 1.4 需要小心的地方

**(a) 成功轨迹不等于正确的接口**

旧模型的成功轨迹带着旧模型自己的习惯。论文发现，回退率与解决率无关：Gemini 3.1 Pro 回退编辑占 14.3%，GPT-5.4 只有 1.2%，两者分数却几乎一样（p.10，*Backtracking is decoupled from solve rate* 段）。

【推断】新模型走的路不同，不一定是错的。如果按旧轨迹去修 harness，可能会把新模型往旧模型的风格上拉，这正是作者批评的“overfit one model's quirks”（p.3）。

**(b) 修改应该针对接口，而不是行为风格**

论文允许的修改只有两类：推理 nudge 和工具接口（p.8，§5.1 *One shared harness, minimal family adapters* 段）。

【推断】对比轨迹时，应该优先找接口层面的差异，例如工具调用格式、错误类型，而不是“旧模型先测试再编辑”这类策略上的差异。

### 1.5 附带的 bug：什么时候该拿旧模型来对比

关键是先判断失败是不是 harness 不适配造成的。论文里有几种信号可以借用：

| 信号 | 含义 | 原文依据 |
|---|---|---|
| 真实工具错误率升高（R8 = `tool_invocation`） | 调用在执行前就失败了，例如工具名不对、参数不合法、old_str 找不到。这类错误多半是接口问题，不是推理问题 | p.21，表 4 R8；p.36，§A.3 *Per-model genuine tool-error rate* 段：Grok 的 file_write 错误率约 44%，原文称之为 “tool-contract mismatch”，而不是推理失败 |
| 缓存命中率异常 | 对话内容被篡改或前后不一致 | p.103，§G.1 第 1 段 |
| 空的工具调用、重复的无效调用 | 模型在按字面执行 prompt，或者在为一个它看不见的错误反复背锅 | p.5，§3.2 第 3 段；p.2，图 1 |
| 稳定复现 | 每题跑 5 次，排除随机波动 | p.8，§5.1 第 2 段 |

【建议】一个可行的触发条件：
1. **只对“旧组合稳定成功、新组合稳定失败”的题目做对比**，例如旧模型 5 次里成功 4 次以上，新模型 5 次里最多成功 1 次。这样可以排除随机波动。
2. **新模型的失败轨迹里要有接口层的信号**（见上表）。如果新模型只是推理错了、改错了地方，工具调用却都正常，那多半是能力或风格的问题，不应该改 harness。
3. **用 D(t) 找偏离点**：看新旧轨迹从哪一步开始分叉。如果分叉处对应一次工具报错或一次反馈缺失，就是 harness 的问题。

### 1.6 需要注意的混杂因素

| 因素 | 影响 | 原文依据 |
|---|---|---|
| 评测环境本身有问题 | 有的实例即使补丁正确也会失败 | p.13，*A few residual evaluation artifacts cap the achievable ceiling* 段 |
| SWE-Pro 的 git 历史泄露 | 旧模型的“成功”里可能有一部分来自偷看答案，拿这些轨迹当参照会把方向带偏，应该改用 Sanitized 环境 | p.12–13，§5.5；p.71，附录 B |
| 基础设施 | TB2 上的超时、延迟、带宽都会造成失败，这类失败既不是模型的问题，也不是 harness 接口的问题 | p.11，§5.4 第 1 段 |

### 1.7 当前判断

【推断】这个思路有道理，尤其适合定位接口层的问题。gpt-oss 的例子说明，这类问题修好后收益可能很大。但“效果会好很多”仍然只是假设，论文没有验证。它能否成立，取决于能不能把**接口失败**从**能力失败**和**风格差异**中分离出来，1.5 节列出的信号可以帮助做这个区分。

这也对应论文的一个结构性缺口：作者分别展示了“对齐的 harness 能跑出官方分数”和“轨迹能区分模型”，但没有把两者连起来。

### 1.8 与 HarnessX 问题 1 的关系

HarnessX 问题 1 见 `../HarnessX_论文整理/候选问题.md`：模型升级时，用旧模型当 meta-agent 会不会更好？

**相同点**：场景相同。两者都是模型升级后把旧 harness 直接交给新模型，并且都想利用“旧模型”作为资源。

**不同点**：研究的变量不同。

| 维度 | HarnessX 问题 1 | SSA 问题 1（本问题） |
|---|---|---|
| **核心问题** | **谁**来改 harness 效果更好？ | 用**什么数据**、在**什么情况下**改 harness？ |
| 研究的变量 | meta-agent 是谁：旧模型还是 frontier 模型 | 诊断时用的输入：只看新模型的失败轨迹，还是同时对比旧组合的成功轨迹 |
| 旧模型的角色 | **老师**：亲自读轨迹、提出修改 | **参照物**：只负责跑出成功轨迹，供对比使用 |
| 关键难点 | 弱老师能否诊断强学生；旧模型的经验存在参数里还是存在演化历史里 | **归因**：新模型的失败是 harness 不适配造成的，还是能力或风格问题造成的 |
| 谁来改 harness | 已经限定为 meta-agent | 没有限定，人或 agent 都可以 |
| 主要依据 | HarnessX 的 meta-agent 设定和演化历史文件 | SSA 的 R8 错误分类、D(t)、gpt-oss 修复的例子 |

一句话：**HarnessX 问题 1 研究“谁当医生”，本问题研究“拿什么做诊断、什么时候该开药”。**

**为什么可以单独成立**【推断】
1. **两个变量正交**。可以固定改 harness 的一方，只改变输入数据，单独检验本问题；也可以固定输入，只换 meta-agent，单独检验 HarnessX 问题 1。
2. **本问题有独立的贡献点，即“失败归因”**：先判断失败是不是 harness 造成的，再决定要不要修改。HarnessX 问题 1 没有涉及这一点，它默认所有失败都交给 meta-agent 处理。
3. **两者可以组合**。本问题提供更好的诊断输入，HarnessX 问题 1 决定由谁使用这份输入。

**重叠点的核对结果**（核对的是 HarnessX 原文，2026-10-16）

需要核对的问题是：HarnessX 问题 1 的条件 D（frontier meta-agent + 阶段 0 的演化历史）是否已经包含了“旧组合的成功轨迹”。

| 文件 | 内容 | HarnessX 原文依据 |
|---|---|---|
| `data/task_history.jsonl` | 每个 (round, task) 一行，是逐题的记录，**不是完整轨迹** | p.43，附录 E.1 目录结构（“one line per (round, task)”） |
| `R<n>/trajectories/*.jsonl` | 每轮的原始 rollout | p.43，附录 E.1（“raw rollouts”） |
| `R<n>/digests/*.md` | 逐题的失败分析 | p.43，附录 E.1（“per-task failure analysis”） |
| Planner 读的跨轮历史 | journal.md、ship_outcomes.json、rejected_candidates.jsonl、task_history.jsonl（用来找“持续失败的题”） | p.30，附录 B，Planner prompt |

结论：
- HarnessX 问题 1 第 1.4(b) 节定义的“演化历史”只有 journal、ship_outcomes、task_history、rejected_candidates，**不含原始轨迹**。所以条件 D **没有**覆盖本问题的“新旧轨迹对比”。
- 不过，阶段 0 的运行目录里**确实存有**旧组合的原始轨迹（`R<n>/trajectories/`），把它提供给 meta-agent 在技术上可行。这正是两个问题可以组合的接口。
- **未核实**：raw rollouts 是否同时包含成功和失败的轨迹，HarnessX 原文没有明说。

**可选的组合实验**【建议】：在 HarnessX 问题 1 的条件 D 基础上增加一个条件 D′，让 frontier meta-agent 同时读取阶段 0 的旧组合成功轨迹，并加上 1.5 节的归因筛选。比较 D 与 D′，可以单独测出“新旧轨迹对比”这一输入的贡献。
