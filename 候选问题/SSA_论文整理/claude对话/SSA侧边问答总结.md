## 速查：概念一句话

| 概念 | 一句话解释 |
|---|---|
| Docker | 一种轻量的“环境打包与隔离”工具：把程序和它依赖的一切装进一个隔离的容器里运行 |
| 镜像 / 容器 | 镜像是只读的模板（“菜谱”），容器是由镜像启动、可读写、彼此隔离的运行实例（“做出来的一盘菜”） |
| 循环逻辑 | SSA 的核心循环：调用模型 → 执行工具 → 追加结果 → 重复，直到模型说结束或达到轮数上限 |
| 适配器（adapter） | 每家厂商一个，把各家 API 的原始回复翻译成同一套七类事件 |
| 七类事件 | assistant text、reasoning content、tool-use requests、stop reasons、usage、cache metadata、recoverable errors |
| 追加结果 | 把工具执行的结果接到对话记录末尾，下一轮模型就能看到上一步发生了什么 |
| 无状态 API | 模型不记得上一次说过什么，每轮都要把整段对话重新发一遍 |
| 前缀缓存 | 每轮只在末尾加新内容，前面部分不变，服务端可以复用缓存；正常情况下命中率逐步接近 1.0 |

## 一、Docker

### 1. Docker 是什么？有什么作用和用途？

**是什么**：一种容器化技术。它把程序和运行所需的一切（操作系统层的文件、依赖库、配置、环境变量）打包在一起，放进一个彼此隔离的环境里运行。可以类比为把整个房间打包成标准集装箱，运到哪台机器上，打开都是原样。

**核心概念**

| 概念 | 是什么 | 类比 |
|---|---|---|
| 镜像（Image） | 只读模板，包含一个环境的全部文件和配置 | 安装光盘、菜谱 |
| 容器（Container） | 由镜像启动的运行实例，可读写，彼此隔离 | 按菜谱做出来的一盘菜 |
| Dockerfile | 描述如何构建镜像的脚本 | 菜谱的写法 |
| 仓库（Registry） | 存放和分发镜像的地方，如 Docker Hub | 应用商店 |

一个镜像可以同时启动很多个容器，每个容器都从同样的初始状态开始，互不干扰。

**和虚拟机的区别**

| | 虚拟机 | Docker 容器 |
|---|---|---|
| 隔离方式 | 模拟整台计算机，各自运行完整的操作系统 | 共享宿主机内核，只隔离进程、文件系统和网络 |
| 启动速度 | 分钟级 | 秒级 |
| 资源占用 | 大 | 小 |
| 隔离强度 | 更强 | 稍弱，但大多数用途已经足够 |

**主要作用**：环境一致（解决“我电脑上能跑，你电脑上跑不了”）、隔离、可复现、可以限制资源、易于分发。

**常见用途**：软件部署、统一开发环境、CI/CD 测试、微服务，以及科研评测（保证实验环境可复现）。

### 2. Docker 在 SSA 论文里起什么作用？

| 作用 | 说明 | 原文依据 |
|---|---|---|
| 给 agent 一个沙箱 | agent 会执行命令、改代码、装依赖、删文件；在容器里改坏了也只影响这一个容器 | p.3，§2 第 1 段（“we use Docker for all our experiments”）；p.4，图 2（“Docker sandbox or local”） |
| 统一每道题的初始状态 | SWE-Bench 每个实例有标准镜像，代码 checkout 在 base_commit；21 个模型 × 5 次运行都从同一个起点开始 | p.8，§5.1 第 3 段 |
| 求解与评测分离 | 把 agent 的改动导出成补丁，放到另一个独立的评测容器里重放并跑测试，所以临时文件和构建产物必须排除在最终 diff 之外 | p.8，§5.1 第 2 段 |
| 控制资源和网络 | SWE 基准关闭网络，TB2 开启；TB2 限制每个任务的内存、CPU 和时间 | p.8，§5.1 第 3 段；p.11，§5.4 |

**两点提醒**：
- **容器隔离的是环境，不是物理资源。** 同一节点上并发运行多个容器（如 Harbor 的 `n_concurrent > 1`）会分摊网络带宽，导致依赖下载变慢（p.11，§5.4 第 1 段）。
- **容器不会替你清理镜像里本不该有的信息。** SWE-Bench-Pro 的公开镜像保留了“未来”的 git 对象，agent 用 `git log -p`、`git show` 就能看到答案（p.12–13，§5.5）。作者的 Sanitized 做法是在 agent 开始之前清掉 remotes、refs 和未来的提交（p.71，§B.1）。

**一句话**：在 SSA 这类 agent 评测中，Docker 为每次运行提供一个干净、一致、隔离、可控的沙箱，让 agent 可以放心执行命令，也让不同模型之间的比较可以复现，比较才公平。

## 二、SSA 的核心循环

### 3. “各家 API 各不相同，但统一转换成七类事件后，循环逻辑只需写一套”是什么意思？

**循环逻辑**就是 §2 的核心循环（p.4，*Agent core and conversation* 段：“call the model, execute requested tools, append tool results, and repeat”）。【示意】

```python
messages = [system_prompt, user_prompt]          # 初始对话

for step in range(max_iterations):               # 最多 500 轮（附录 C，p.74）
    reply = call_model(messages)                 # ① 调用模型
    if reply.stop_reason == "end_turn":          # 模型说“我做完了”
        break
    for call in reply.tool_requests:             # ② 模型要求调用工具
        result = run_tool(call.name, call.args)  #    在 Docker 里执行
        messages.append(result)                  # ③ 把结果追加到对话里
                                                 # ④ 回到开头，再问模型
```

**各家 API 的差异**【示意，具体以各家文档为准，论文没有列出这些细节】：

| 厂商 | “我要调用工具”大致的样子 |
|---|---|
| Anthropic | 回复中有 `type: "tool_use"` 的内容块 |
| OpenAI | 回复中有 `tool_calls` 列表 |
| Gemini | 回复中有 `functionCall` 部分 |
| gpt-oss（经 vLLM） | 原始输出是 Harmony 格式的 token 流，要先由服务端解析成 OpenAI 格式（附录 G） |

**如果不统一**，循环里就要到处写 `if provider == ...` 的分支，每加一家厂商都要改一遍循环。

**SSA 的做法**：在循环外加一层适配器，每家一个，把原始回复翻译成七类统一事件（p.4，*Model interface* 段）。

```
Claude 原始回复 ──→ [Anthropic 适配器] ──┐
GPT 原始回复    ──→ [OpenAI 适配器]    ──┼──→ 统一事件 ──→ 同一个循环
Gemini 原始回复 ──→ [Gemini 适配器]    ──┘
```

原文的说法是：“The event loop is the same across all models.”

**这对论文为什么重要**：
- 【推断】**比较公平**：21 个模型跑在同一个循环里，轨迹差异才更有把握归到模型本身。原文没有明说这是设计目的。
- **差异被限制在可控的地方**：按家族不同的只有 prompt 和绑定的工具，循环本身不变（p.8，§5.1 *One shared harness…* 段）。
- **方便排查问题**：作者从 cache metadata（缓存命中率异常为零）入手查出了 gpt-oss 的解析问题（p.103，§G.1），又把解析错误统一成 recoverable errors 来重试修复（p.106，§G.4）。

**一句话**：适配器负责把五种“方言”翻译成同一种“普通话”，循环只听得懂普通话，所以只需写一套。

### 4. “追加结果”是什么意思？

**含义**：把工具执行后的输出接到对话记录的末尾，下一次调用模型时，模型就能看到上一步的结果。

**为什么要追加**：模型 API 是无状态的，不记得上一次说过什么，每轮都要把整段对话重新发一遍。附录 G.2 原文：“At every turn, the harness resubmits the conversation as a structured JSON”（p.104）。图 2 的图注也写着循环会 “append tool results to conversation state”（p.4）。

**例子**：第 1 轮模型请求 `ls /testbed`，harness 在 Docker 里执行后，把结果追加进记录：

```
[system]      你是一个能操作电脑的助手……
[user]        请修复这个 issue：……
[assistant]   调用 bash: ls /testbed           ← 模型的请求
[tool_result] command: ls /testbed             ← 新追加的结果
              exit code: 0
              output: setup.py  src/  tests/ …
```

第 2 轮把整段记录再发给模型，模型看到目录结构，再决定下一步。如此反复。

**SSA 追加的内容是结构化的**（p.4，§3.1）：
- 每次 shell 调用返回 command、status、exit code、output、error text；
- 超时时返回已有的部分输出；
- 输出太长时截掉中间、保留首尾；
- 编辑成功后返回 unified diff。

这对应引言的第二个核心问题：模型是否得到了关于 harness 所做之事的准确描述。**追加什么、怎么写，就是“环境 → 模型”这个方向的鸿沟所在。**

**由此带来的两个连锁问题**：
1. **对话越来越长**：需要 conversation manager 压缩大输出或裁剪旧轮次，同时保证每个工具调用和它的结果成对出现，不能拆开（p.4，*Agent core and conversation* 段）。
2. **前缀可以缓存**：正常情况下命中率应该逐步接近 1.0。gpt-oss 的命中率中途突然掉到 0，说明发回去的对话与服务端缓存的不一致，作者由此查出了 Harmony 解析问题（p.103，§G.1 第 1 段）。

## 三、研究思路讨论

### 5. 模型升级后，用“新模型失败轨迹 + 旧组合成功轨迹”修改 harness，效果会不会好很多？

> 这一问后来整理进了 [候选问题.md](../候选问题.md) 的问题 1，并补充了与 HarnessX 问题 1 的关系（见主对话总结第 6、7 节）。这里只保留要点。

**结论**：论文没有做过这个实验，所以从原文里得不出“效果会不会好很多”的答案。

**支持这个思路的证据**：
- 换模型后，旧优化可能失效（p.3）；对 Claude 有效的定量 nudge 会让 Gemini/Grok 发出空调用凑数（p.5）。
- harness 侧的问题修好后收益可能很大：gpt-oss-120b 从 42% 提高到 64.64%（p.106）。
- solution distance 本来就用其他模型的成功运行作为参照（p.22），D(t) 可以用来定位新旧轨迹的分叉点。

**需要小心的地方**：
- 成功轨迹不等于正确的接口。回退率与解决率无关（p.10），照着旧轨迹修改，可能把新模型往旧风格上拉。
- 修改应该针对接口（工具格式、错误类型），而不是行为风格（p.8）。

**附带的 bug：什么时候该拿旧模型来对比？** 先判断失败是不是 harness 造成的：

| 信号 | 原文依据 |
|---|---|
| 真实工具错误率升高（R8 = `tool_invocation`） | p.21，表 4；p.36（Grok `file_write` 错误率约 44%，原文称之为 “tool-contract mismatch”） |
| 缓存命中率异常 | p.103，§G.1 |
| 空工具调用、重复的无效调用 | p.5，§3.2；p.2，图 1 |
| 5 次运行中稳定复现 | p.8，§5.1 |

【建议，论文里没有】触发条件：只对“旧组合稳定成功、新组合稳定失败”的题目做对比；失败轨迹里要有接口层的信号；再用 D(t) 找分叉点。

**混杂因素**：评测环境本身的问题（p.13）、SWE-Pro 的 git 泄露（p.12–13，应改用 Sanitized 环境）、TB2 的基础设施问题（p.11）。

## 侧边问答中值得记住的几点

1. **容器隔离 ≠ 信息隔离**。git 泄露说明，镜像里有什么，agent 就能看到什么。评测的可信度取决于镜像本身是否干净。
2. **“追加结果”正是 intent-execution gap 中“环境 → 模型”方向的具体落点**。§3.1 的结构化反馈，就是在规定追加什么、怎么写。
3. **缓存命中率是一个廉价的诊断信号**。前缀缓存的原理决定了正常的命中率应该接近 1.0，一旦掉到 0，就说明对话内容在某处被改动了。gpt-oss 的问题就是这样发现的。
4. **统一事件接口既是工程上的便利，也是实验上的控制**：它把模型之间的差异限制在 prompt 和工具这两处。
